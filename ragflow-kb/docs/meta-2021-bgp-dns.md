# Meta 2021-10-04 全球故障：骨干维护命令误断 + DNS 自动撤回 BGP 放大

- 受影响服务：dns / 骨干网 BGP（全局）
- 影响范围：global
- 来源复盘：https://engineering.fb.com/2021/10/05/networking-traffic/outage-details/

## 当时可见症状（值班视角）
- 公共解析器对 facebook/instagram 等返回 SERVFAIL；外部观测到其 IP 前缀 BGP 路由被撤回
- 访问流量趋近于零；内部依赖 DNS 的工具与远程管理通道同时不可用
- 服务进程本身一直在运行——问题不是'服务器挂了'，而是'找不到服务器了'
- 工程师只能进机房，高等级物理安全又拖慢了进入速度

## 红鲱鱼（当时错误假设）
- 容易被误判为 DNS 服务进程故障或遭受攻击，实际是路由层不可达

## 真实根因
一条评估骨干容量的维护命令误将骨干网全部连接断开（审计工具 bug 未拦截）；数据中心孤立后，DNS 服务器按安全设计撤回 BGP 广播（本该屏蔽单点不健康，却因全部同时触发而放大为全局不可达）；恢复受阻于内部工具与带外通道同样依赖已故障的网络/DNS。

## 决定性排查步骤
- 先分层定位：解析失败（DNS 层）vs 路由不可达（BGP 层）vs 应用错误——本例是名字根本解析不了 （事故特有，需领域推理）
- 从外部视角检查自己前缀的 BGP 广播是否被撤回（不只看内部监控） （事故特有，需领域推理）
- 识别'保护机制'变成了放大器：DNS 不健康即撤回路由的设计在全部同时触发时适得其反 （事故特有，需领域推理）
- 识别恢复路径自身受损：内部工具与带外访问依赖同一套已故障的系统，需带外/物理通道 （事故特有，需领域推理）
- 把故障起始时间与维护窗口的命令/变更关联（骨干维护命令） （通用样板，不计分）

## 关联的变更 / 运维操作
- 15:39 例行维护执行骨干容量评估命令（审计工具有 bug 未拦截，实际断开骨干全部连接，无变更单）

## 止血与处置
止血：恢复 BGP 广播（需进机房物理操作，因带外通道依赖同一网络）。根因修复：修复审计工具、为 DNS 撤回策略加抑制（避免全局同时撤回）。动作分级：改 BGP/全局关 WAF 属最高风险（T4），必须审批。

## 可复用的经验雷点
- 安全保护机制要防'全部同时触发'的放大器效应
- 维护/容量评估命令必须过审计拦截，且先在隔离范围验证
- 恢复通道不能依赖被它恢复的系统（带外/物理兜底）
