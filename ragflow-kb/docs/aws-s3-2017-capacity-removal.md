# AWS S3 2017-02-28 us-east-1 故障：运维命令参数输错下线过多服务器

- 受影响服务：s3（us-east-1 对象存储：index 元数据/位置 + placement 存储分配）
- 影响范围：region
- 来源复盘：https://aws.amazon.com/message/41926/

## 当时可见症状（值班视角）
- us-east-1 S3 请求大面积失败，错误率与延迟同时抬升（GET/LIST/PUT/DELETE 全失败）
- 依赖 S3 的 EC2 新实例启动、EBS（快照恢复）、Lambda、S3 控制台连带报错
- index/placement 子系统容量被下线的服务器占比过大，触发完整重启
- AWS 状态页自身依赖 S3，无法更新（只能发 Twitter）

## 红鲱鱼（当时错误假设）
- 容易先怀疑容量不足或代码 bug，但真因是运维操作

## 真实根因
运维人员调试计费子系统慢查询时，按既定 playbook 执行容量下线命令，一个参数输入错误，导致下线了支撑 index（元数据/位置）与 placement（存储分配）两个基础子系统的大量服务器；两子系统需要完整重启，而该规模下多年未被完整重启过，恢复链路未经受考验，重启+校验耗时约 4 小时。

## 决定性排查步骤
- 先查最近一小时有没有运维操作/命令执行（谁在动容量），再怀疑容量或代码 bug （事故特有，需领域推理）
- 区分是哪个子系统不可用（index vs placement）以及容量是否低于下限 （事故特有，需领域推理）
- 评估恢复路径本身的耗时风险（从未完整重启过的子系统，RTO 是未知数） （事故特有，需领域推理）
- 梳理依赖级联（S3 之外还有谁挂在上面：EBS/Lambda/EC2/控制台） （事故特有，需领域推理）

## 关联的变更 / 运维操作
- 09:37 S3 团队成员按既定 playbook 执行容量下线命令（一个参数输错，实际下线远多于预期的服务器；无变更单）

## 止血与处置
止血：停止继续下线、谨慎按子系统重启恢复（index 先、placement 后）。动作分级：容量下线/重启属高风险（T3），必须审批；恢复路径漫长需提前通告。

## 可复用的经验雷点
- 容量下线/节点摘除类命令必须二次确认目标范围，参数错误代价极大
- 多年未完整重启的核心子系统，其 RTO 是未知数——要常态化演练
- 状态页/控制台不能依赖自身服务，否则事故中失声
