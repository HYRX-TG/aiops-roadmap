# GitHub 2018-10-21 MySQL 脑裂：43 秒网络分区引发 24 小时降级

- 受影响服务：mysql-cluster（Orchestrator 管理的主备）
- 影响范围：global
- 来源复盘：https://github.blog/2018-10-30-oct21-post-incident-analysis

## 当时可见症状（值班视角）
- Orchestrator 显示的复制拓扑里只剩西海岸机房的服务器；站点大面积错误
- webhook 与 Pages 构建大量积压；用户看到前后不一致的数据
- 复制滞后：数十个只读副本落后主库数小时；积压 500 万+ webhook、8 万 Pages 构建
- 跨大陆往返延迟约 60ms，应用无法承受

## 红鲱鱼（当时错误假设）
- 容易被当成数据库自身故障，实际根因在网络维护引发的分区

## 真实根因
例行维护更换光模块造成东西海岸 43 秒网络分区；Orchestrator 把分区判定为主库故障并跨区提升西海岸副本为主库；链路恢复后两个机房各自接受了对方没有的写入（事实上的脑裂/双主），无法安全切回。放大因素：Orchestrator 跨区提升策略本身是放大器；跨大陆 60ms 延迟让东海岸应用基本不可用；恢复路径（从远端备份恢复数 TB）从未整体演练过，耗时远超预期（总降级约 24 小时）。

## 决定性排查步骤
- 把数据库异常与刚刚发生的网络维护（43 秒断连）关联，而不是当成数据库自身故障 （事故特有，需领域推理）
- 识别出现了双主/脑裂：两岸各自接受了对方没有的写入，这才是不能简单切回的原因 （事故特有，需领域推理）
- 识别自动故障切换策略本身成了放大器（Orchestrator 跨区提升主库） （事故特有，需领域推理）
- 明确'数据完整性 > 可用性'的取舍，并识别恢复路径自身耗时（备份恢复数小时、副本滞后按幂衰减） （事故特有，需领域推理）
- 先查最近变更/发布（通用样板） （通用样板，不计分）

## 关联的变更 / 运维操作
- 2018-10-21 22:52 计划维护更换故障 100G 光模块，造成东西海岸骨干断连 43 秒（网络分区，计划维护）

## 止血与处置
止血与恢复：从备份重建集群 → 同步副本 → 回切原拓扑 → 处理积压（三步走）。备份每 4 小时一次，恢复数 TB 耗时数小时；恢复完还要等副本追平（滞后按幂衰减）。动作分级：从备份恢复属不可逆数据操作（B 类，restore_from_backup），必须审批；优先保数据完整性（暂停 webhook/Pages）。

## 可复用的经验雷点
- 自动故障切换（Orchestrator 跨区提升）要防'分区即提升'的脑裂放大器
- 网络维护窗口与数据库高可用强相关，43 秒分区足以引发双主
- 恢复路径（备份恢复数 TB）必须演练，否则 RTO 远超预期
