# Cloudflare 2019-07-02 全球故障：WAF 正则灾难性回溯耗尽边缘 CPU

- 受影响服务：edge-proxy（全球边缘代理/WAF）
- 影响范围：global
- 来源复盘：https://blog.cloudflare.com/details-of-the-cloudflare-outage-on-july-2-2019/

## 当时可见症状（值班视角）
- 13:45 起全网 502 错误率飙升，客户域名访问返回 502，全球流量下降约 80%
- 多个 PoP 的 HTTP/HTTPS 服务 CPU 核心接近 100%（基线 <40%）
- 首批告警来自 WAF 合成功能测试失败（外部探针），不是用户报障
- Cloudflare 自己的 Dashboard/API/状态页/Jira 都走同一条边缘链路，同样不可用（控制面受损）

## 红鲱鱼（当时错误假设）
- 值班初判疑似前所未见的大规模攻击（DDoS）或容量不足——均为红鲱鱼

## 真实根因
13:42 防火墙团队通过自动流程部署了一条新的 WAF 托管规则，其中含灾难性回溯正则（形如 .*(?:.*=.*)），在真实请求体上指数级回溯，耗尽所有 HTTP 服务核心 CPU。叠加因素：数周前的 WAF 重构移除了 CPU 过度使用保护；SOP 允许规则不经灰度直接全球推送；回滚需要完整重跑两次 WAF 构建；控制面与数据面同链路导致修复工具自身不可用。

## 决定性排查步骤
- 按组件拆分 CPU 数据，定位到是 WAF 进程在吃 CPU，而不是泛泛的'CPU 高' （事故特有，需领域推理）
- 把 CPU 饱和起始时间与 13:42 的 WAF 规则部署做时间关联（变更关联） （事故特有，需领域推理）
- 识别控制面与数据面同链路受损，需要带外通道/紧急开关（全局关闭 WAF） （事故特有，需领域推理）
- 先查最近变更/发布，再怀疑攻击或容量（攻击假设是红鲱鱼） （通用样板，不计分）

## 关联的变更 / 运维操作
- 13:42 防火墙团队经自动流程部署含灾难性回溯正则的 XSS 检测 WAF 托管规则（不经灰度全球推送）

## 止血与处置
止血：全局紧急关闭 WAF 托管规则（带外/紧急开关，因控制面同链路受损需绕行）。根因修复：修正正则、恢复 CPU 保护、规则改为灰度推送、修复工具解耦控制面。动作分级：全局关 WAF 属高风险（影响安全防护），需 SRE on-call 审批。

## 可复用的经验雷点
- 正则/规则类变更要做回溯复杂度审查，宁可慢不可全球直推
- 控制面与数据面必须解耦，否则修复工具会在事故中自残
- 看到 CPU 100% 先按组件拆，别停在'CPU 高'这一层
