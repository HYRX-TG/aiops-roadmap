SRE / AIOps · 项目解剖

这个项目到底是什么，它是怎么跑起来的

一句话：它不是"AI 自动运维系统"，而是三样东西：① 一个中英双语、可交互的 AIOps/SRE 知识图谱；② 一条真实可跑的告警处理流水线（降噪 → 分级 → 研判 → 护栏 → 审批 → 审计）；③ 一套用真实事故和真实系统验证"大模型能不能自己查出根因"的测试台。

最新一轮（2026-10-26）补了三块：中英双语切换（293/300 节点有中文译文）、RAGFlow 真实事故知识库接线（6 大公开复盘，含 mock 端到端验证）、Dify 工作流骨架（可直接导入）。同时修掉了切语言后 UI 外壳不跟着变的问题。

先记住这个"医院"类比，全文都会用到

把整套系统想成一家医院的急诊科：告警 = 病人涌进来，去重 = 同一个人别重复挂号，门控 = 门口筛掉来推销的，分流 = 分诊台按轻重缓急排队，RAG = 先翻病历库，LLM = 会推理的主治医生，护栏 = 手术前的风险分级和家属签字，dry-run 计划 = 手术方案推演，审计 = 手术记录留档。你只要记住这条链路，代码就是它的实现。

The big picture

1 · 这项目到底是什么

它是三块东西拼在一起，分别用两种语言写。这一点必须最先搞清楚，否则你会在"为什么有 Node.js 又有 Python"里迷路。下面先看产品两块，第三块（测试台）单独讲。

半球 A · 知识图谱（改的）

一个可以逛的 SRE 学习地图

底座是 GitHub 开源项目 MansoorMajeed/infra-roadmap（MIT 协议）。原版就有：13 个分区、300 个知识节点、节点之间用"学习者会问的问题"连边、只展开下一步、⌘K 搜索、浏览器本地存进度。

你（让 Agent）做的改造：全站中英双语（293/300 节点有译文，可一键切换）、新增 aiops 分区 7 个节点、节点详情页里加了一个 AI 助手面板、告警会把节点染红、深色模式。

技术栈：Next.js 16 + React 19 + TypeScript + Tailwind v4 + React Flow。用 output:"export" 纯静态导出，能直接丢到 nginx/CDN，不需要服务器。

半球 B · 研判后端（写的）

一条真的能跑的告警处理流水线

目录 backend/，Python + FastAPI（但核心逻辑故意只用标准库，方便单测）。它做的事是：接告警 → 降噪 → 分级 → 研判 → 护栏 → 出执行计划 → 人工审批 → 记审计。

它自带一个可视化大盘 /dashboard（不用前端也能演示），一个压测脚本 bench/flood.py，一套 117 个单测。

关键认知：后端不依赖前端。你只起 backend，打开 :8600/dashboard 就能完整演示一遍。前端只是另一个"客户"。

为什么是两个半球？这是原项目作者的取舍，也是你的机会

原项目是纯静态的知识图谱——它故意不做后端，所以任何人都能 fork 完直接部署。要往上加 AI 能力，有两个选择：

❌ 塞进 Next.js 的 API Route

Next.js 的 output:"export" 是"导出静态 HTML"，不支持服务端路由。想做后端就得放弃纯静态部署，原来的优势没了。而且 Node 里做重计算/长任务不如 Python 顺手。

✅ 拆一个独立 Python 服务

前端继续纯静态、零成本部署；后端独立演进、独立测试、独立扩容。两者通过 HTTP + localStorage 里存的地址解耦。缺点是多一个进程要起，且浏览器跨域（CORS）必须自己配——这正是当前项目最大的坑。

第三块：测试基建（vm-agent/ + ragflow-kb/）

这不是产品代码，是这个项目最有说服力的部分。它分成四个层次，一层比一层严格：

层次目录测什么回答的问题

为什么测试基建比功能更值钱

因为第一轮测试的故障是直接写进日志的字符串——那不是测试，是自问自答。后面每一轮都在修上一轮的方法学缺陷：真实注入 → 训练集/留出集分离 → 走真实接入层而不是塞 prompt → 让模型自己调工具取证。

这条"不断发现自己测试在骗自己"的演进线，本身就是最好的面试故事。详见 9.5 节。

Glossary

2 · 术语表：先把词弄懂，代码就不吓人了

下面每个词都给你三层：它是什么意思 → 这个项目里怎么用 → 类比。看不懂就跳过，读完第 5 节再回来。

告警（Alert）

监控系统发现"指标不对"时发出的一条消息。比如"支付服务错误率 > 5%"。

本项目：7 种来源的告警最终都被转成同一个结构 UnifiedAlert。

告警风暴（Alert Storm）

一次故障会瞬间产生成百上千条告警，人根本看不过来，反而漏掉真正重要的那条。

本项目：用去重 + 门控把 1 万条压到 3 千条（压测数据）。

指纹（Fingerprint）

给每条告警算一个"身份证号"。同样的事算出来同一个号。

本项目：(来源, 告警名, env/service/instance/namespace/host/system/cluster) 做 JSON 排序后 SHA1 取前 16 位。

类比：同一个人同一件事，只发一张号。

滑动窗口去重

不是"永远只留一条"，而是"最近 N 秒内同一个指纹最多放行 M 条"。

本项目：默认窗口 300 秒、每窗口最多 1 条（IngestPipeline）。

类比：门卫记着"这人 5 分钟内已经进过 3 次了，别放了"。

门控（Gate）

去重之后再做一层规则过滤，按"业务价值"丢垃圾。

本项目 4 条规则：测试环境、心跳/探活、无影响的 info、维护窗口。每条规则单独计数。

类比：前台筛掉推销、查水表、发传单的。

分诊 / 分流（Triage）

按严重程度打 P0–P3，再决定走哪条处理路径。

本项目：可解释评分 → P0/P1 → research（进 AI 主链路）、P2 → batch（低峰批处理）、P3 → notify（只通知，0 Token）。

P0 / P1 / P2 / P3

P0 是"业务全挂，立刻全员起床"；P3 是"知道了，明天看"。

本项目评分：critical 基础 5 分，命中"支付/下单/退款"等词 +2，核心服务 +1，影响用户 ≥1000 +2，工单 +0.5。≥8 是 P0，≥5 是 P1，≥3 是 P2，其余 P3。

RCA（根因分析）

不是"哪里报错了"，而是"为什么会这样"。

本项目：研判阶段输出根因假设 + 排查链 + 验证命令，而不是一句话结论。

Runbook / 剧本

把"这类故障应该怎么查"写成固定步骤。本项目：playbooks.py 里有 7 个剧本，每个都含排查步骤、只读命令、判据、安全动作、需审批动作。

RAG（检索增强生成）

让大模型先"翻资料"再回答，而不是凭记忆瞎编。

本项目：rag.py 调 RAGFlow（本地知识库）检索历史故障复盘和 Runbook；没配就返回一段 mock 文档兜底。

类比：开卷考试，先翻书再答题。

LLM / 可插拔大脑

大语言模型。项目里有两个大脑：规则兜底（关键词匹配剧本）和真 LLM（任意 OpenAI 兼容端点，如 DeepSeek）。配了环境变量就用 LLM，没配就规则。

护栏（Guardrail）

AI 想动生产环境时，必须先过的关卡。核心原则：只读自动放行，写操作默认要人批，冻结期一律拦。

本项目：T1–T4 风险分级 + 爆炸半径 + 冻结窗口 + 审批人 + 审计。

爆炸半径（Blast Radius）

一个操作最坏会影响多大范围。

本项目：pod < node < namespace < cluster，超过配置上限就强制人工审批。

dry-run 计划

只生成"如果执行会做哪几步"，不真的动刀。

本项目：pipeline_research.py 的 plan 阶段输出步骤、爆炸半径、审批人，状态 pending_approval。

人在回路（Human-in-the-loop）

AI 只出建议，最终动作由人拍板。

本项目：/api/approve 是唯一能"放行"的入口；计划里明写"执行权在人，永不静默自动执行"。

工作流 / checkpoint

把一次处理拆成多个阶段，每阶段跑完就"存档"，进程挂了能接着跑。

本项目：workflow.py，SQLite 存 current_stage + context，每阶段独立重试 + 指数退避。

类比：游戏存档。

SLO / on-call（了解即可）

SLO 是"服务承诺达到什么水平"，on-call 是"谁值班负责"。项目里审批人字段（SRE on-call）就是这套制度的体现。

这张图最重要的一句话

3.5.1 双语：内容翻译 + UI 外壳

实现方式朴素但有效：中英双语写在同一个 Markdown 文件里，用注释标记分段。

content/<zone>/<slug>.md

一份文件、两种语言

---
title: "Hello, World!"
title_zh: "“你好，世界！”"
---
英文正文...

<!-- ZH_SUMMARY -->
中文摘要...

<!-- ZH_DEEP_DIVE -->
中文深入...

<!-- ZH_RESOURCES -->
中文资源...

<!-- ZH_UI -->
1. 里程碑1的中文
2. 里程碑2的中文
3. 问题边的中文
4. 问题详情的中文

content.ts 在构建期按 <!-- ZH_* --> 切分，产出 summaryZh / deepDiveZh / resourcesZh，并把 ZH_UI 的编号列表按固定顺序还原（里程碑 → 每条边的 question → 每条边的 detail）。

src/lib/i18n.tsx

UI 外壳文案表

内容双语只解决了"正文"。按钮/标题/提示仍是硬编码中文——这就是本轮发现的真 bug：切到 EN 后正文变了、外壳没变，看起来像"切换失败"。

修法：加一张 STRINGS 表 + useT() 钩子。缺 en 回退 zh，缺 key 回退 key 本身（漏配立刻看得出来）。

同时给两类对象加了 title_en：节点 frontmatter、以及 _zones.yaml 的 13 个分区标题。

检查项结果

面试时怎么说这块

"双语不是把页面复制两份，而是内容与外壳分开治理：内容用标记块内联双语（构建期切分，运行时零开销），外壳用文案表 + t()。ZH_UI 按位置还原是唯一脆弱点，我写了校验脚本扫全部 300 篇确认 0 错位。原创中文分区我不假装翻译——EN 模式下显式提示。"

3.5.2 RAGFlow 事故知识库

ragflow-kb/ 把 6 个公开事故复盘做成知识库，可一键导进 RAGFlow。

incident_docs.py

6 篇结构化复盘

每篇含：当时可见症状、红鲱鱼（当时的错误假设）、真实根因、决定性排查步骤、关联变更/操作、止血处置、可复用经验。

覆盖 Cloudflare 2019 / AWS S3 2017 / GitLab 2017 / Meta 2021 / Fastly 2021 / GitHub 2018。

build_kb.py

一键建库

建库（中文 naive 切块）→ 上传 md → 批量解析 → 轮询 → 抽检检索。跑完打印 DATASET_ID，填进 RAGFLOW_DATASET_IDS 即接通。

支持云端 Starter / 自托管；本地地址强制不走代理（否则被 VPN 拦）。

verify_ragflow.py

零依赖契约验证

起一个 mock RAGFlow（实现 v0.27.2 契约 + 内置微型索引），用项目真实的 RagClient 去查它。

验三件事：真实实例优先 / 未配置回退 mock / 实例不可达也回退（不报错）。

实测：三项全过，真实路径返回 sim=0.500 的 Fastly 文档。

⚠️ 必须知道的评测污染风险（我实测确认了）

这 6 篇知识库文档正好就是 replay / heldout 评测用的那 6 个事故，且每篇都含「## 真实根因」。

我用 mock RAGFlow 拿 Fastly 的告警症状去查，召回第一条就是：

# Fastly 2021-06-08 全球 CDN 中断：客户合法配置触发数周前部署的软件 bug

泄漏关键词：真实根因 根因 bug 合法。

结论：接 RAGFlow 后端跑评测，分数会虚高，不可信。当前默认不配 RAGFlow（走 mock 兜底），所以评测仍有效。生产用真实内部知识库没这个问题——"给模型看历史复盘"是合理产品行为，只是不能拿同一批数据做评测。

已加固：ragflow-kb/check_eval_contamination.py 可一键检测。

3.5.3 Dify 工作流骨架

alert-diagnosis-workflow.yml 是可导入 Dify 的工作流 DSL：开始（alert 输入）→ LLM RCA 诊断 → 结束。

LLM 节点要求输出固定结构：告警摘要 / 可能根因（按概率排序）/ 影响范围 / 建议处置 / 紧急等级。定位是"执行层（StackStorm / Ansible）的大脑"。

本轮修掉的一个真 bug

Trace one alert

5 · 一条告警的完整旅程（七幕）

这是最值得反复读的一节。假设虚拟机上的支付服务开始刷错误日志，我们跟着它走完整个系统。

第 1 幕 · 探针发现异常（虚拟机上）

agent.py 每 2 秒 tail 一次 /var/log/demo-app.log。10 秒窗口内攒够 3 条含 ERROR/FATAL/Exception 的行，就触发上报。

上报前先跑 investigate.sh：kubectl get pods、ps aux --sort=-%cpu、free -m、systemctl status、uptime、/var/log/changes.log（变更台账），把输出截断到 4KB。

它发出去的 JSON 长这样：

POST http://192.168.197.1:8600/api/ingest
{
  "source": "business_log",
  "payload": { "events": [ {
      "level": "error",
      "event": "log_ERROR_payment_callback_timeout_seq_3",
      "message": "2026-10-25 09:29:43 ERROR payment callback timeout",
      "service": "vm-app-2", "env": "prod",
      "ts": "2026-10-25T09:29:46",
      "investigation": "### 1. Pod 状态\n... ### 6. 系统服务健康\npayment-api: inactive ..."
  } ] }
}

注意 event 的生成规则：先剥掉行首时间戳再派生。否则每条日志时间不同 → 指纹全不同 → 去重完全失效。这是一个非常真实的坑。

第 2 幕 · 归一化 + 算指纹（后端）

normalize_any("business_log", payload) 把事件变成 UnifiedAlert：severity "error" → critical，labels 里塞进 service/env，raw.investigation 保留证据。

然后 __post_init__ 自动算指纹：把 {source, alertname, env, service, instance, namespace, host, system, cluster} 按 key 排序做 JSON，SHA1 取前 16 位，得到类似 3f5f65f505837246。

为什么要排序：dict 顺序不同会导致同样的内容算出不同的哈希。sort_keys=True 保证稳定。

第 3 幕 · 去重 → 门控 → 分级

去重：同一指纹在 300 秒窗口内已经有过一条 → 判重复，rejected_by_dedup += 1，直接丢。

门控：env 是 test？是心跳？是 info？在维护窗口？——都不是，放行。

分级：critical 基础 5 分 + 标题含"payment"命中业务关键词 +2 + 核心服务 +1 = 8 分 → P0 → route=research，reasons 里写清三项依据。

放行的告警被 IngestStore.record() 写进 ingest.db，/api/alerts 就能读到它。

这里有一个必须知道的事实

分级算出 route=research 之后，没有任何代码自动调用研判。你需要在 /dashboard 上点"⚡ 送研判"，或者手动 POST /api/research。所以严格说，它是"自动分级 + 人工触发研判"，不是全自动闭环。

第 4 幕 · 建 run + ① enrich_context

点"送研判" → POST /api/research，body 里是 {source, alert: <alert_json>}。

ResearchPipeline.run() 先 engine.start()：生成 12 位 run_id，把 alert + triage 存进 research.db 的 runs 表（current_stage=0）。

然后跑第 1 个 stage：拼一个查询串（标题 + 描述 + service），调 RagClient.retrieve()；同时从 alert.raw.investigation 取出探针证据。

产出写回 context：{rag_hits, rag_backend, investigation}，然后 checkpoint(stage_idx=1)。这一行就是"存档"。

第 5 幕 · ② judge 研判

把告警、分级、RAG 命中、探针证据拼成 prompt，调用大脑。

LLM 模式的 system prompt 里有三条铁律：①只能基于给定证据下结论，缺证据写进 uncertain；②有停机/数据风险的处置必须放 approval_required；③命令必须只读。

规则模式则用 match_playbooks() 按关键词打分选剧本，输出"命中《资源抢占》"这类结论，并明确写"规则兜底未做根因推理，请人工确认"。

输出结构（两种模式一致）：

{
  "root_cause": "命中排查剧本《资源抢占》：...",
  "confidence": "medium",
  "investigation": [ { "step": "确认影响面", "finding": "...", "evidence": "..." } ],
  "verification": [ "kubectl get pods -A | grep -v Running" ],
  "remediation": {
    "safe":              [ { "action": "给吵闹邻居设 CPU Limit", "downtime": "none" } ],
    "approval_required": [ { "action": "删除吵闹邻居 Pod", "downtime": "full",
                             "approver": "对方 owner + SRE" } ]
  },
  "known": ["..."], "inferred": ["..."], "uncertain": ["..."],
  "recommendation": "...", "sources": ["runbook/..."]
}

第 6 幕 · ③ guardrail 护栏

从根因 + 建议的文本里猜动作（回滚/扩容/重启/摘流/观察），再查风险登记表。

假设识别到 rollback：T3 > 自动放行阈值 T1 → needs_approval=True，reason 写"风险等级 T3 超过自动放行阈值 T1，需人工审批"。

当前代码的致命缺口

如果文本里一个关键词都没命中，detect_action 返回 None，调用方 or "observe" 把它当成"只读观察"→ 直接放行。这意味着"建议删除生产数据库"这种建议可以绕过审批。正确做法是识别不出就当最高风险。

第 7 幕 · ④ plan + 人工审批 + 审计

如果研判结果里有处置分级，plan 阶段直接把 🟢/🔴 两类动作写成 dry-run 步骤，state=pending_approval，并带上爆炸半径和审批人；没有的话用 _PLAN_TEMPLATES 里的通用模板。

人在大盘上点"✅ 确认执行"或"❌ 拒绝" → POST /api/approve → 护栏再判一次 → 写一条审计 → 返回 {executed, guardrail, msg}。

注意当前实现：审批只写进程内 list，不校验 run 是否存在、不校验动作是否匹配、不把 plan.state 改掉、重启就丢——这是"演示态"而不是"生产态"。

把这七幕压缩成一句话（面试可以直接说）

"一条告警进来，先被归一化成统一模型并算指纹，然后在 300 秒窗口里做去重、再过四条业务价值规则，接着按可解释评分分成 P0–P3；P0/P1 进一条四阶段持久化工作流：先检索知识库和现场证据，再让大模型或剧本做根因分析，然后过护栏做风险分级，最后生成 dry-run 计划交人审批；全程每阶段存档，可断点续跑，每次审批都留审计。"

7 · 核心机制拆解

7.1 指纹：为什么这个设计能降噪

如果两条告警"看起来一样"，系统怎么知道它们是同一件事？答案是只取"身份相关"的字段，忽略时间、描述里的随机数。

FINGERPRINT_LABEL_KEYS = ("env","service","instance","namespace","host","system","cluster")

payload = {"source": source, "alertname": alertname, **{k: labels.get(k,"") for k in KEYS}}
blob    = json.dumps(payload, sort_keys=True, separators=(",",":"))
fingerprint = sha1(blob).hexdigest()[:16]     # 16 位十六进制，够用且好读

为什么 sort_keys=True 是必须的：Python dict 保序，但不同来源拼出来的 key 顺序可能不同；不排序同样的内容会算出不同哈希，去重直接废掉。

为什么 instance 要进指纹：同一个告警在 10 台机器上发生，是 10 个不同事件，不该被合并。反过来，日志事件如果每条带唯一 trace_id 进指纹，就永远去不了重——所以探针在派生 event 时故意剥掉时间戳和随机 trace。

7.2 分级评分：为什么用"可解释加法"而不是模型

score = severity_base        # critical 5 / warning 2 / info 0.5
      + 2  (标题描述命中"支付/订单/退款/auth..."等业务词)
      + 1  (service 或文本命中 api/gateway/db/redis/kafka 等核心组件)
      + 2  (labels.affected_users >= 1000)
      + 0.5(来源是工单，说明已有人确认)

P0 >= 8   P1 >= 5   P2 >= 3   其余 P3
research = {P0, P1}   batch = {P2}   notify = {P3}

为什么不用模型打分：①分级决定"要不要花钱调 LLM"，必须极快、极稳、可复现；②出了问题要能向老板解释"为什么这条是 P0"；③模型有幻觉风险，而分级错了会直接导致漏处理或烧钱。这是"该用规则的地方就用规则"的典型判断。

7.3 工作流引擎：150 行怎么替代 Temporal

Temporal 是业界常用的"持久化工作流"服务，能力很强，但要部署一整套服务 + 学 SDK。这个项目是单机自用，所以作者选择用 SQLite 自己实现三个核心语义：

Temporal 能力本项目实现关键代码
持久化（进程挂了不丢进度）每阶段结束写 runs.current_stage + context 到 SQLitecheckpoint()
节点级重试 + 退避每个 Stage 有自己的 max_retries 和 backoff_seconds，失败按 base * 2^attempt 等待WorkflowEngine.run() 内层 while
失败可观测每次尝试都写 stage_log（stage/attempt/ok/error/ts），run 最终标 failedlog_stage() / finish()
断点续跑启动时扫 status IN (running, failed) 的 run，从 current_stage 继续resumable_runs() / resume_all()
每次 stage 成功即 checkpoint；进程重启后从 current_stage 续跑，已完成阶段不重跑。

7.4 研判输出：为什么是"四段式"而不是一段话

项目里所有研判结果都被拆成四类，这是整个设计里最有工程品味的一点：

🟢 已知

有直接证据支撑的事实。例："告警源 business_log，分级 P0，评分 8.0"。

🟡 推测

基于证据的合理推断。例："时间线与一次发布吻合，可能是发布引起"。

⚪ 无法确认

缺少数据，明说不知道。例："未接入指标源，CPU 是否饱和无法确认"。

💡 建议

下一步动作，且标注风险等级和是否需要审批。

为什么这很重要：纯 LLM 系统最大的问题是"不知道也说得很确定"。四段式把"不确定性"变成一个必须在界面上显示的字段，从结构上逼模型诚实。测试报告里那个 S3 场景（CPU 饱和）LLM 主动写"告警文本仅为疑似，尚未确认"，就是这套 prompt 约束起作用。

7.7 前端知识图谱的三个关键机制

① 为什么"只展开下一步"（渐进式披露）？

300 个节点全画出来是一团毛线，人会直接关掉。所以初始只显示起点和它的直接下一步，用户点开一个才展开它的邻居。节点之间的连边不是"下一章"，而是学习者会问的一句话——比如"我老是 SSH 上去手动改，有没有更好的办法？"。这让学习路径变成"顺着好奇心走"，而不是背目录。

② 内容为什么能"只改 Markdown 就生效"？

因为 content.ts 在构建时（不是浏览器里）用 Node 的 fs 读所有 md，gray-matter 拆 frontmatter，zod 校验字段，然后按 <!-- DEEP_DIVE --> 标记切成三段。校验不过直接构建失败。所以内容是"编译进静态 HTML"的，这也是它能离线、能 CDN 托管的原因。

③ 进度为什么不用数据库？

因为这个产品的定位是"零后端、无账号、随便部署"。进度只存在你自己的浏览器 localStorage 里，键名 infra-roadmap-progress。代价是换设备就没了，所以额外做了"导出/导入 JSON"来兜底。这是一个很清楚的取舍：用隐私和零运维换掉账号系统。

Tradeoffs

8 · 为什么这样设计（面试最容易被追问的部分）

每个"为什么不用 X"都要能讲出取舍，而不是"我不会"。下面这些是这个项目里真实存在的设计决策。

为什么不用 Temporal？

答：单机自用项目引入 Temporal = 多一个有状态服务 + 一堆运维成本 + SDK 学习成本，收益不匹配。我用 SQLite checkpoint 实现了它的三个核心语义（持久化 / 节点级重试 / 断点恢复），约 150 行，每行讲得清，而且语义对齐，未来要迁也平滑。

追问"那规模大了怎么办"：当出现多机、高并发、需要可视化工作流、需要定时/信号能力时，就该迁 Temporal 或 Argo Workflows。判断标准是是否需要跨进程协调，不是"够不够酷"。

为什么核心逻辑用纯 stdlib？

答：为了可测。业务逻辑不 import FastAPI，就能直接用 unittest 跑，不需要起服务、不需要 mock 框架。FastAPI 只做参数解析和返回 JSON 的薄壳。依赖越少，测试越快，逻辑越容易讲。

为什么前端纯静态导出？

答：知识图谱是"内容型产品"，没有用户数据、没有个性化服务端逻辑，纯静态就能部署到任何地方（nginx / GitHub Pages / CDN），成本接近零。代价是不能用 Next 的 API Route，所以后端拆成独立 Python 服务——这不是妥协，是边界清晰。

为什么 mock 兜底？

答：演示可靠性。面试/展示时网络或本机服务随时可能挂，RAG 和 LLM 都是外部依赖。没有 key 也能完整讲完故事。代价是必须让人知道"现在是 mock 还是真的"——这个项目的大盘做得不错（显示 backend 连接状态），但前端面板做得不好（静默回退，看不出来），这是要修的。

为什么 P2 走 batch、P3 只通知？

答：成本与注意力都是稀缺资源。LLM 调用有真金白银的成本，值班工程师的注意力更贵。P3（比如证书还有 30 天过期）进大模型是浪费；P2 可以攒着低峰批处理。这条设计让 81.5% 的接入量不碰 LLM——但注意这个分母口径有问题，见第 9 节。

为什么护栏要放在服务端？

答：前端代码用户能改。放在前端的"审批"不是审批，是装饰。密钥、风险表、冻结窗口开关、审计都必须只在服务端。前端那份 guardrails.ts 只是演示等价逻辑，注释里也这么写了。这个意识比代码本身更值钱。

工具组 4/4，而且路径是我没提示的：查变更（发现合作伙伴 14:05 把配额 500→5000）→ 查指标（l2 的 quota_limit_effective 一直 500，直到 14:35 才变）→ 查队列（requests_over_quota_silently_queued 从 0 飙到 94000）→ 查拓扑 → 结论"l2 缓存 TTL=1800s 导致配额延迟 30 分钟生效，期间静默排队"。

训练数据里没有这个场景。它真的在用工具推理，不是背答案。

另一个案例：它自己想到了复盘里的关键判据

W2 它自己走了这条路：看自己 → 看拓扑（发现 upstream 是交换机）→ 24h 查不到就自动试 7d → 查交换机审计（找到 43 秒光模块维护）→ 对比两岸写入速率（东岸 8200→0，西岸 7900→0→8100→8300） → 看日志确认 two primaries detected → 结论双主/脑裂。

"对比两岸写入速率"这个判据我完全没提示——那是复盘里定位脑裂的决定性证据。

9.5.5 能力边界（强弱都实测过）

强项

  • 会用工具、遵守协议：28 次调用 0 次无效
  • 会选查证顺序：看自己 → 看拓扑 → 扩大窗口 → 查审计 → 交叉验证
  • 会自动扩大搜索范围（24h 查不到就试 7d / 30d）
  • 会在虚构场景推理（W4 拿 4/4）
  • 会主动标注不确定（输出含 uncertain 字段）
  • 能查真实系统（动态 16/16）

弱项

  • 没工具就基本归零（虚构场景 0/4）
  • 容易被错误数据带偏（工具 bug 时 W1 掉到 1/4）
  • 真实噪声会干扰（D4 曾把宿主机负载误判为根因）
  • 不会主动要求缺失的数据（只会换查法，不会说"请接入 X 指标"）
  • 证据齐不齐决定上限（B 13/16 vs C 16/16）
  • 不知道自己该停（靠 prompt 提醒"只剩 2 步"才收敛）
我在测试台里修掉的三个 bug（都值得记）

① 窗口过滤用了真实时间。用 2026 的时间去筛 2021 年的变更，所有变更查询返回空。模型被工具骗了，误判"近期没有变更"——W1 从 4/4 掉到 1/4。模型没变，数据错了。

② 多实例伪装成单实例。Windows 的 SO_REUSEADDR 允许多进程绑同一端口。杀掉 state.json 记录的 PID，另一个残留实例还在响应，于是"进程被杀"这个故障根本没发生，测试却当成发生了——这是差点写进报告的假阳性。

③ 32 核机器上 8 个 hog 压不出抢占。实测抢占比只有 0.91×（阈值 1.35×）。改单核绑定后 8.92×，且机器总负载只有 1 核。

第 ① 条本身就是结论：智能运维平台第一优先级不是模型，是数据可信度。

9.5.6 结论：怎么才能变成真正的智能运维平台

三组数字定义了边界：10/16（无工具）→ 13/16（给了工具）→ 16/16（证据全给）。A→B 是"给它查证能力"，B→C 的 3 分全是"它没查到"。

第一优先级

可观测性数据层（决定上限）

按对根因的贡献排序：变更/部署时间线、运维操作审计、指标时序（当前完全缺失）、服务拓扑/CMDB、结构化日志检索。

没有这五样，模型再强也只能猜。这不是模型问题，是数据工程问题。

第二优先级

工具设计（决定可用性）

  • 返回结果要带"可用选项"（查不存在的指标时告诉它有哪些）
  • 空结果要区分"没有"和"查不到"
  • 保留原始性，不要替它总结（别替它做关联）
  • 只读白名单 + 危险命令前置拦截
第三优先级

Agent 编排（决定稳定性）

  • token 预算（实测约 1–2K / 步）
  • 并行取证（现在串行，可省一半时间）
  • 收敛判据（改成"关键证据齐全度"检查）
  • 人机协作点（高危动作必须停下等人）
不建议做的三件事

① 别让模型"自己发现该监控什么"——实测它只会查已有指标，监控体系是人的设计。
② 别让模型直接执行修复——它确实会尝试 rm / kubectl delete，护栏设计是对的。
③ 别用关键词评分验收——同一个答案关键词给 2/4、LLM 评审给 4/4。要用"根因是否正确 + 推理链是否成立"。

完整数据与工具调用链：vm-agent/agentic/INTELLIGENT-OPS-VERDICT.md、AGENTIC-RESULTS.md、DYNAMIC-RESULTS.md。可复现：python run_agentic.py --api-key ... / python run_dynamic.py --api-key ...

30 秒版（开场就甩）

"我做了一个 AIOps 方向的工程项目，分三层。上层是一个中英双语的 SRE 知识图谱，13 个分区 300 个节点，纯静态部署；中层是我自己写的 Python 研判后端，把一条告警从接入到处置建议的完整链路跑通了：9 类数据源归一化、指纹去重、四条规则门控、P0–P3 可解释分流，然后是四阶段持久化工作流——RAG 检索、可插拔 LLM 研判、护栏风险分级、dry-run 计划，最后人工审批留审计。

但我最想讲的是第三层：我用一个测试台回答了'大模型到底能不能靠思维链路解决运维问题'。三组对照：只给症状 10/16，给它一套只读工具让它自己查 13/16，证据全摆好 16/16。所以答案是能，但瓶颈在数据不在模型。我还在一个完全虚构、不可能出现在训练数据里的事故上验证过：单轮 0/4，工具自主 4/4。"

三个判断：该用规则的地方不用模型（降噪和分级全是确定性逻辑）、AI 永远不许直接执行（护栏在服务端，高危动作必须人批）、没有指标就没有真相（我自己重做了四轮测试基建，每轮都在修上一轮'测试在骗自己'的问题）。"

3 分钟版（按"问题 → 设计 → 取舍 → 结果 → 边界"）

  1. 问题：一次故障会产生几千条告警，人看不过来；直接全丢给大模型又贵又不安全。
  2. 设计：分层降噪（去重 25% + 门控 43%），只把 P0/P1 送进 AI；AI 的输出强制拆成"已知/推测/无法确认/建议"；所有动作过护栏，写操作必须人批。
  3. 取舍：不用 Temporal，用 150 行 SQLite checkpoint 实现持久化/重试/续跑；核心逻辑纯 stdlib 以便单测；前端纯静态导出，后端拆独立服务。
  4. 结果：117 个后端单测 + 46 个前端全过；1 万条压测降噪 67.9%；规则大脑 10/24 → LLM 24/24；四个真实故障场景全部命中剧本并给出分级处置；自愈闭环 4/4（真注入、真修、独立探针验证）；智能体自主排查：静态 13/16、动态真实系统 16/16。
  5. 边界：执行层是 dry-run 没接真实集群；前端跨域和 payload 契约还有 bug；审批缺鉴权和持久化审计。这些我都知道在哪、怎么修。

高频追问 + 怎么答

Q：你怎么证明"大模型能解决运维问题"？

"我没法证明'能'，我只能量出边界。三组对照：只给症状 10/16、给只读工具让它自己查 13/16、证据全摆好 16/16。

关键在设计：我把答案放在环境里而不是 prompt 里，模型必须自己调工具查。而且加了一个完全虚构的事故（两层网关配额缓存 TTL 不一致），训练数据里绝对没有——单轮组拿 0/4，工具组拿 4/4，它自己按'查变更→查指标→查队列→查拓扑'走出来的。

这组数字的含义是：推理不是瓶颈，数据可得性才是瓶颈。B 组比 C 组少的 3 分，全是'它没查到'而不是'它推不出来'。"

Q：你这不是调了几个 API 吗？有什么技术含量？

"调 API 不是难点。难点是在什么条件下才调：我要先证明只有 18.5% 的量值得调，还要证明调完的结果不会直接动生产。所以我的工作主要是三块——降噪链路、工作流的可恢复性、以及护栏的失败方向。这三点任何一块做错，系统在生产里都是负资产。"

Q：你的 LLM 会不会瞎编？

"会，所以我从结构上约束：prompt 里写死三条铁律（只能基于证据、有停机风险必须进审批、命令必须只读），输出强制分成四段，其中'无法确认'是必须显示的字段。测试里有个 CPU 故障场景，模型确实主动写了'告警文本仅为疑似，尚未确认'，而不是硬编一个根因。另外规则兜底模式永远在，LLM 不可用就降级。"

Q：为什么不用 LangChain / Dify / HolmesGPT？

"调研过，但我的自研价值在'接线和治理'而不是'能力'。HolmesGPT 的 RCA 思路我借鉴了（工具调用 + 证据链），RAGFlow 直接接、没重写，LLM 用任意 OpenAI 兼容端点。真正必须自己写的是：多源归一化的字段口径、去重指纹的定义、分级评分规则、以及护栏的风险表——这些是公司特有知识，开源替不了。"

Q：生产上量了怎么办？

"当前瓶颈很明确：单条 SQLite commit，实测 42–76 条/秒。上生产第一件事是把写入改成批量/消息队列（Kafka + 消费者），接入层本身是纯内存计算，横向扩很容易；工作流要迁 Temporal；审计要落独立库；告警流要分页和保留期。这些都是有明确路径的工程问题，不是架构问题。"

Q：你怎么保证 AI 不乱动生产？

"三道：①护栏在服务端，前端改不了；②只读动作可自动，写动作默认要审批，冻结窗口一律拦，爆炸半径超限一律拦；③执行层只出 dry-run 计划，真实执行交给 StackStorm/Ansible 并保留审批链。不过我要诚实说：现在'动作识别'那一步有 fail-open 的 bug——识别不出关键词会落到'观察'直接放行，正确做法应该是识别不出就当最高风险。这个我已经定位到了。"

Q：这个项目你最大的收获是什么？

"第一轮测试我用写死的日志字符串造故障，8 个场景规则大脑判了 7 个'依赖超时'。我当时第一反应是'模型不行'，但复盘发现是测试在骗自己——故障根本没有真实发生。后来我重做了整套测试基建：真进程、真配置变更、真看门狗测延迟、真变更台账。这件事让我明白，AIOps 里最难的不是模型，是可观测性和证据链。"

三条红线：这三句话千万别说

① "前后端都完全打通了" —— 前端真的不通。② "吞吐 11 万条/秒" —— 那是纯函数，不是系统。③ "审批是服务端强制关卡，很安全" —— 缺鉴权、fail-open。主动说边界，比被问出来强十倍。

12 · 吃透它的学习路径

Step 4 · 读研判与剧本（45 分钟）

pipeline_research.py → judge.py → playbooks.py（先读 1 个剧本的完整结构）。目标：能说出"四段式输出"每个字段对应什么、LLM prompt 的三条铁律是什么、规则模式为什么只能在剧本覆盖范围内工作。

Step 5 · 读护栏与服务壳（40 分钟）

guardrail.py → server.py。目标：能画出护栏决策树；能列出 /api/approve 当前缺什么（鉴权、run 校验、状态回写、持久化）。

Step 6 · 读前端"数据怎么变成界面"（40 分钟）

content.ts + validation.ts → NodeGraph.tsx → ContentPanel.tsx（只看 AiAssistantPanel）。目标：能解释"为什么内容能在构建时编译进去"、"为什么告警能染红节点"、"AI 面板为什么失败后看不出来"。
