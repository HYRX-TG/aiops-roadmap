# 告警风暴压测报告

> **口径声明（重要，2026-10-25 修订）**：本项目有两组数字，用途不同，**不要混用**：
> - **进程内纯函数吞吐**（`bench/flood.py`）：验证接入层算法本身（归一化/去重/门控/分流）的性能上限。
> - **端到端 HTTP 吞吐**（`_bench_http.py`，本报告实测）：含 HTTP 解析、JSON 序列化、SQLite 落库，
>   才是"系统每秒能接多少条告警"的真实答案。
>
> 曾经的错误：把纯函数吞吐（11 万条/秒）当成系统吞吐写进文档——差约 1500 倍，
> 面试官一追问就露。现在两个口径都如实记录。

## 1. 进程内纯函数吞吐（bench/flood.py）

- 风暴规模：**10,000 条**（60% 重复与低信噪比噪声），单进程串行接入
- 吞吐：**114,650.9 条/秒**（总耗时 0.087s）
- 用途：证明接入层算法不是瓶颈；**不代表系统吞吐**

## 2. 端到端 HTTP 吞吐（实测，2026-10-25，本机）

| 模式 | QPS | 说明 |
|---|---|---|
| 短连接（每条新建 TCP） | **37.2** | 最坏情况 |
| keep-alive（连接复用） | **93.2** | 探针/前端常态 |

瓶颈定位：**SQLite 每条告警一次 commit**（接入层落库）。优化路径：批量写（`executemany`
+ 定时 commit）或换消息队列（Kafka/Redis Stream）——预期可到数千 QPS。
这条结论本身就是面试素材："我会量，并且知道瓶颈在哪、怎么改"。

## 3. 降噪与分流（10,000 条风暴，纯函数层）

| 指标 | 数值 |
|---|---|
| 接入总量 | 10,000 |
| 滑动窗口去重拦截 | 2,500 |
| 入口门控拦截 | 4,287 |
| **综合降噪率** | **67.9%** |
| 放行进后端 | 3,213 |
| P0/P1/P2/P3 | 367 / 1484 / 787 / 575 |
| research 主链路 / batch / notify | 1851 / 787 / 575 |

## 4. Token 口径（修订）

| 说法 | 数值 | 口径 |
|---|---|---|
| ~~Token 节省 81.5%~~ | — | **废弃**：以接入总量为分母，把"本来就会被门控丢掉的噪声"算成了节省 |
| **LLM 主链路占比** | **18.5%** | 1851 / 10000（进 LLM 的接入量比例） |
| **相对全量进模型省** | **42.4%** | 1 - 1851 / 3213（以放行量为分母，守得住追问） |

推荐话术："分流后只有 18.5% 的接入量进 LLM 主链路；相对'放行的告警全量进模型'省 42%"。

## 5. 时延（本机实测，模拟 RAG + 规则研判）

| 阶段 | P50 | P95 |
|---|---|---|
| 接入层纯逻辑（去重+门控+分流） | 0.008 ms/条 | 0.012 ms/条 |
| 研判主链路端到端（样本 30，规则大脑） | 70.0 ms | 100.4 ms |

> 注意：研判 P95 是**规则大脑**口径；接真 LLM（DeepSeek）后单次研判约 1-3s，
> 所以平台只让 P0/P1 进主链路——分流不只是省 Token，也是延迟预算。

> 复现：`python bench/flood.py --total 10000`（纯函数） / `python _bench_http.py`（端到端 HTTP）
