## Cloudflare 2019-07-02 全球故障（WAF 正则回溯耗尽 CPU）

- 来源（官方复盘）：https://blog.cloudflare.com/details-of-the-cloudflare-outage-on-july-2-2019/
- 真实根因（跑前固定）：13:42 部署的新 WAF 托管规则含灾难性回溯正则（.*(?:.*=.*)），在真实请求体上指数级回溯，耗尽所有 HTTP 服务核心 CPU；叠加因素：数周前的 WAF 重构移除了 CPU 过度使用保护、SOP 允许规则不经灰度直接全球推送、回滚需要完整重跑两次 WAF 构建、控制面与数据面同链路导致修复工具自身不可用。
- 决定性步骤（跑前固定；➖=通用样板不计分）：
  1. ✅ 按组件拆分 CPU 数据，定位到是 WAF 进程在吃 CPU（而不是泛泛的'CPU 高'）
  2. ✅ 把 CPU 饱和起始时间与 13:42 的 WAF 规则部署做时间关联（变更关联）
  3. ➖ 先查最近变更/发布，再怀疑攻击或容量（攻击假设是红鲱鱼）
  4. ✅ 识别控制面与数据面同链路受损，需要带外通道/紧急开关（全局关闭 WAF）

### 平台原始输出（逐字）

**根因判定**：13:42 防火墙团队自动部署的 XSS 检测 WAF 托管规则触发 edge-proxy 的 HTTP/HTTPS 服务进程 CPU 饱和（全 PoP 接近 100%），导致上游连接失败并返回 502，全球流量下降约 80%；时间线上规则部署（13:42）先于合成测试失败与 502 刷屏（13:45+），且前置 Web 服务器 CPU 尚有余量但无法触达后端 HTTP 服务进程，指向边缘 HTTP 服务进程被规则处理逻辑耗尽而非容量不足或外部攻击。

**置信度**：medium · **大脑**：openai:deepseek-chat

**排查链**：
- [核对变更与告警时序] WAF 托管规则部署发生在 13:42，合成测试失败、端到端失败、502 与流量下降均在 13:45 之后出现，变更先行于故障。
- [确认资源瓶颈位置] 瓶颈在 HTTP/HTTPS 服务核心 CPU 接近 100%（基线 <40%），而前置 Web 服务器仍有余量 CPU，说明请求已到达边缘但后端 HTTP 服务进程无法处理。
- [核对错误日志语义] 日志显示 upstream connect error 与 front line 生成的 502，符合边缘 HTTP 服务进程不可用/过载时的表现。
- [评估影响面与控制面] Dashboard、API、状态页、Jira 同走边缘链路而不可用，说明故障位于边缘数据面而非单一客户或单一 PoP。
- [排除人为假设] 值班初判的 DDoS 与容量不足缺乏证据支撑，且与变更时序及前置服务器余量矛盾。

**验证命令**：
- `kubectl get pods -n edge-proxy -o wide（只读，确认 edge-proxy 实例状态与分布）`
- `kubectl top pods -n edge-proxy（只读，确认 HTTP/HTTPS 服务进程 CPU 现状）`
- `curl -s -o /dev/null -w '%{http_code}\n' https://<customer-domain>/（只读，复现 502）`
- `查询 WAF 变更单与规则下发记录（只读审计日志，确认 13:42 规则版本与生效范围）`
- `查询 edge-proxy 上游依赖成功率与连接错误计数（只读指标，对应 Runbook《依赖超时处置 v2》第一步）`

**🟢 可自动处置**：冻结 WAF 托管规则的进一步自动下发与自动回滚，避免变更窗口内二次扰动；按 Runbook 确认影响面：统计各 PoP 502 比例、CPU 曲线与规则生效范围的对应关系
**🔴 需审批处置**：回滚 13:42 部署的 XSS 检测 WAF 托管规则至上一版本（brief·SRE on-call（T3 高风险动作，需审批））；对 edge-proxy HTTP/HTTPS 服务进程扩容（T2 半自动）（rolling·SRE on-call）

**修复覆盖对照**：复盘里真正止血的动作是「全球关闭 WAF（kill switch），把有问题的规则路径整体摘掉」（复盘原文：先尝试局部关闭未果，13:52 决定全球关闭 WAF，14:02 生效后 CPU 恢复正常）→ 平台**没覆盖到** ❌（白名单对应动作：disable_waf_rule）

## AWS S3 2017-02-28 us-east-1 故障（运维命令参数输错删错服务器）

- 来源（官方复盘）：https://aws.amazon.com/message/41926/
- 真实根因（跑前固定）：运维人员调试计费子系统慢查询时，按 playbook 执行容量下线命令，一个参数输入错误导致下线了支撑 index（元数据/位置）与 placement（存储分配）两个基础子系统的大量服务器；两者需要完整重启，而该规模下这些子系统多年未被完整重启过，恢复链路未经受考验，重启+校验耗时约 4 小时。
- 决定性步骤（跑前固定；➖=通用样板不计分）：
  1. ✅ 先查最近一小时有没有运维操作/命令执行（谁在动容量），再怀疑容量或代码 bug
  2. ✅ 区分是哪个子系统不可用（index=元数据/位置 vs placement=存储分配）以及容量是否低于下限
  3. ✅ 评估恢复路径本身的耗时风险（从未完整重启过的子系统，RTO 是未知数）
  4. ✅ 梳理依赖级联（S3 之外还有谁挂在上面：EBS/Lambda/EC2/控制台）

### 平台原始输出（逐字）

**根因判定**：授权人员按 playbook 下线计费子系统服务器时参数输错，导致 S3 的 index（元数据/位置服务）与 placement（存储分配）子系统被过量下线并触发完整重启，S3 无法处理 GET/LIST/PUT/DELETE 请求，全区域 5xx 激增并连带影响依赖 S3 的 EC2/EBS/Lambda/控制台。

**置信度**：high · **大脑**：openai:deepseek-chat

**排查链**：
- [确认故障时间线与触发动作] 09:37 授权 S3 团队成员按 playbook 执行下线命令，参数输错，实际下线服务器远多于预期；09:40+ S3 开始全 API 失败，时间上高度吻合。
- [确认受影响子系统] index 与 placement 子系统容量因过量下线而严重不足，触发完整重启；日志显示两个子系统均在 restarting。
- [确认影响面与恢复过程] 全区域 5xx 激增、成功率骤降；12:26 index 部分恢复后 GET/LIST/DELETE 开始恢复，13:18 index 完全恢复，13:54 placement 恢复后 S3 整体恢复。
- [确认连带依赖影响] S3 控制台、EC2 新实例启动、EBS 快照恢复、Lambda 均报错；AWS 状态页自身依赖 S3 无法更新。
- [对照知识库处置路径] 知识库命中依赖超时处置流程与回滚/扩容分级（回滚 T3 需 SRE on-call 审批，扩容 T2 可半自动），但本次根因是人为误下线而非依赖超时，处置重点应为恢复被下线容量。

**验证命令**：
- `aws s3api list-buckets --region us-east-1（只读，验证 S3 控制面是否可响应）`
- `aws cloudwatch get-metric-statistics --namespace AWS/S3 --metric-name 5xxErrors --region us-east-1 --start-time <T-1h> --end-time <now> --period 300 --statistics Sum（只读，确认错误率趋势）`
- `aws cloudwatch get-metric-statistics --namespace AWS/S3 --metric-name AllRequests --region us-east-1 --start-time <T-1h> --end-time <now> --period 300 --statistics Sum（只读，确认请求量恢复）`

- `aws health describe-events --region us-east-1（只读，核对官方事件与影响范围）`

**🟢 可自动处置**：冻结所有自动化下线/变更脚本，暂停 playbook 自动执行，防止二次误操作；持续只读监控 index/placement 子系统容量与 S3 5xx 指标，确认恢复稳定；核对被误下线服务器清单与实际容量缺口，形成恢复计划

**修复覆盖对照**：复盘里真正止血的动作是「重启/恢复被移除的 index 与 placement 子系统（最终重启了整个 S3 控制面）」（复盘原文：S3 团队必须从完全关闭状态重启控制面，因该子系统从未整体重启过，耗时远超预期）→ 平台**覆盖到了**（白名单对应动作：无）

## GitLab.com 2017-01-31 数据库事故（复制滞后 + 删错主机 + 备份全失效）

- 来源（官方复盘）：https://about.gitlab.com/blog/postmortem-of-database-outage-of-january-31/
- 真实根因（跑前固定）：负载升高→备库复制滞后→WAL 段在主库被回收→人工重建备库过程中，一条删除数据目录的命令执行在了主库（db1）而不是备库（db2），300GB 生产数据几乎全毁；叠加五种备份/复制机制全部静默失效，最终只能恢复到 6 小时前的备份，丢失 17:20-00:00 的数据。
- 决定性步骤（跑前固定；➖=通用样板不计分）：
  1. ✅ 复制滞后先查 WAL 保留/归档：备库需要的段是否已被主库回收（没有 WAL 归档就必然断）
  2. ✅ 任何对数据目录的破坏性操作前，先确认当前主机名/角色（主 or 备）——致命错误就是删错主机
  3. ✅ 别信备份配置，验证备份真的能恢复（复盘里五种备份机制全部静默失效）
  4. ➖ 回溯数小时内的人为操作（17:20 手动快照 + pgpool 实验）与负载突增的关联

### 平台原始输出（逐字）

**根因判定**：命中排查剧本《数据库复制/备份事故（滞后、断链、误删、备份失效）》：数据库事故有三条经典链：①复制滞后→WAL 段在主库被回收→备库断链（没开归档必然发生）；②重建备库时的破坏性操作打在主库上（GitLab 2017 就是这么丢的 300GB）；③备份机制'配了但静默失效'（pg_dump 版本混用、备份桶是空的）。思路：先查复制状态与 WAL 保留 → 再确认主备角色（破坏性操作前必须） → **验证备份真的能恢复**（不信配置，信演练）→ 定位数据丢失窗口。

**置信度**：medium · **大脑**：openai:deepseek-chat

**排查链**：
- [查复制状态与 WAL 保留] 滞后量、断链时间点、WAL 是否被回收、归档是否真的在工作
- [确认主备角色再动手] 当前连接的是主库还是备库——破坏性操作前必须显式确认
- [验证备份真的能恢复] 备份可恢复 + RPO 覆盖故障窗口 → 才敢动手修
- [定位数据丢失窗口] 丢失窗口 = 故障起始 → 最后备份；窗口越小越好

**验证命令**：
- `pg_stat_replication 滞后量回落到秒级`
- `备库 pg_is_in_recovery()=true 且可持续追赶`
- `恢复演练：从选定备份集恢复到临时实例并抽样校验数据`
- `监控告警：复制滞后阈值告警已恢复`

## Meta 2021-10-04 全球故障（骨干命令误断 + DNS 自动撤回 BGP）

- 来源（官方复盘）：https://engineering.fb.com/2021/10/05/networking-traffic/outage-details/
- 真实根因（跑前固定）：一条评估骨干容量的维护命令误将骨干网全部连接断开（审计工具 bug 未拦截）；数据中心孤立后，DNS 服务器按安全设计撤回 BGP 广播（本该屏蔽单点不健康，却因全部同时触发而放大为全局不可达）；恢复受阻于内部工具与带外通道同样依赖已故障的网络/DNS。
- 决定性步骤（跑前固定；➖=通用样板不计分）：
  1. ✅ 先分层定位：解析失败（DNS 层）vs 路由不可达（BGP 层）vs 应用错误——本例是名字根本解析不了
  2. ✅ 从外部视角检查自己前缀的 BGP 广播是否被撤回（不只看内部监控）
  3. ➖ 把故障起始时间与维护窗口的命令/变更关联（骨干维护命令）
  4. ✅ 识别恢复路径自身受损：内部工具与带外访问依赖同一套已故障的系统，需要带外/物理通道
  5. ✅ 识别'保护机制'变成了放大器：DNS 不健康即撤回路由的设计在全部同时触发时适得其反

### 平台原始输出（逐字）

**根因判定**：例行维护中一条本意为评估全球骨干容量的命令实际断开了骨干网全部连接（审计工具 bug 未能拦截），导致数据中心间及数据中心与互联网完全断开；小型机房的权威 DNS 服务器按设计在无法连接数据中心时撤回自身 BGP 广播，所有 DNS 服务器同时自认不健康并撤回路由，全球域名解析返回 SERVFAIL、流量归零。

**置信度**：high · **大脑**：openai:deepseek-chat

**排查链**：
- [梳理故障时间线] 15:39 维护命令误断骨干全部连接，随后权威 DNS 按设计撤回 BGP 广播，15:50 公共解析器缓存过期，21:50 起 BGP 恢复、22:05 DNS 恢复、22:50 服务基本恢复
- [确认 DNS 故障性质] 公共解析器返回 SERVFAIL 而非超时，说明权威服务器不可达，而非解析服务进程崩溃
- [确认路由层证据] Facebook 前缀被大量撤回，Cloudflare 等第三方均观测到
- [确认流量影响] 到 Facebook IP 的流量断崖式下跌，访问流量趋近于零
- [排除服务进程故障] 服务进程本身一直在运行，问题不是服务器挂了而是找不到服务器
- [评估内部处置受阻因素] 远程/带外管理通道不可用，内部工具依赖同一套 DNS/网络而失效，工程师只能进机房且物理安全流程拖慢进入
