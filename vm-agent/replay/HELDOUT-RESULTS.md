## Fastly 2021-06-08 全球 CDN 中断（客户合法配置触发软件 bug）

- 来源（官方复盘）：https://www.fastly.com/blog/summary-of-june-8-outage
- 真实根因（跑前固定）：5 月 12 日部署的软件里有一个未被发现的 bug；6 月 8 日一个客户推送了一次**合法**的配置变更，恰好命中该 bug 的触发条件，导致 85% 网络返回错误。放大因素：新的校验逻辑同步下发到全网（无灰度）；配置校验失败即停止服务，没有回退到上一个好配置的降级路径；验证逻辑与部署逻辑紧耦合，导致校验规则变更立即改变已有生产配置的行为。
- 决定性步骤（跑前固定；➖=通用样板不计分）：
  1. ❌ 先分清 503 是哪一层产生的（CDN 边缘层 vs 源站），而不是被源站被打爆的表象带偏
  2. ✅ 把故障起点与近期的软件版本部署（5/12，数周前）+ 客户侧配置变更做关联
  3. ❌ 识别客户配置是'合法'的：它只是触发器，根因在平台自己的代码里
  4. ✅ 识别 blast radius 是平台全局：同一套校验逻辑同步下发，无灰度、无回退路径
  5. ➖ 先查最近变更/发布（通用样板，不计分）

### 平台原始输出（逐字）

**根因判定**：关联到近期部署（剧本《变更引入故障（跨部门发布/配置变更）》）：Fastly 于 2021-05-12 对 CDN 软件 做了「部署含未发现 bug 的软件（数周前，无灰度同步下发）」（变更单 无）。变更起点与故障起点吻合时，先按变更引入查。

**置信度**：medium · **大脑**：rule

**排查链**：
- [关联近期部署（时间线命中）] Fastly 于 2021-05-12 对 CDN 软件 的部署：部署含未发现 bug 的软件（数周前，无灰度同步下发）（变更单 无）
- [确认影响面] 受影响 Pod 列表 / 错误率 / 健康检查耗时——决定 P0 还是 P2
- [看最近变更] 最近 30 分钟内的 deploy/configmap/secret/scale 事件——有变更先怀疑变更
- [对比变更前后差异] 变更版本号 + 具体 diff（镜像 tag / env / 配置项）
- [确认是变更而非偶发] 错误模式与变更内容强相关（如新配置项导致的启动失败）
- [区分连不上与连上慢] TCP 不通 = 网络/对端宕机；TCP 通但慢 = 对端性能
- [看对端侧证据] 对端 Pod 状态/重启/错误日志

**验证命令**：
- `kubectl rollout status deploy/<svc> -n <ns>`
- `kubectl get pods -l app=<svc> -o wide  # 新副本分布`
- `对比变更前后的错误率曲线（Prometheus/日志计数）`
- `从受害服务节点直接 curl 对端 healthz（绕过服务本身）`
- `对比对端监控的错误率/延迟（认对端还是认自己）`

**🟢 可自动处置**：保留现场，先摘流量观察（不删任何东西）；扩容旧版本副本（maxSurge 滚动，新旧并存）；开启熔断/降级（有预案的话）；切只读副本/备用节点（如果有）
**🔴 需审批处置**：回滚到上一版本（kubectl rollout undo）（rolling·变更发起方负责人 + SRE on-call）；删除他人创建的 ConfigMap/Secret（full·资源 owner + 平台负责人）；重启下游依赖服务（brief·对端 owner + SRE on-call）

**修复覆盖对照**：复盘里真正止血的动作是「禁用/回退触发 bug 的那个客户配置（先止血），之后再部署永久修复」（复盘原文：定位后禁用了该配置，49 分钟内 95% 网络恢复；永久修复 17:25 才开始部署）→ 平台**没覆盖到** ❌（白名单对应动作：无）

## GitHub 2018-10-21 MySQL 脑裂（43 秒网络分区引发 24 小时降级）

- 来源（官方复盘）：https://github.blog/2018-10-30-oct21-post-incident-analysis
- 真实根因（跑前固定）：例行维护更换光模块造成东西海岸 43 秒网络分区；Orchestrator 把分区判定为主库故障并跨区提升了西海岸副本为主库；链路恢复后两个机房各自接受了对方没有的写入（事实上的脑裂/双主），无法安全切回。放大因素：Orchestrator 的跨区提升策略本身是放大器；跨大陆 60ms 延迟让东海岸应用基本不可用；恢复路径（从远端备份恢复数 TB）从未整体演练过，耗时远超预期。
- 决定性步骤（跑前固定；➖=通用样板不计分）：
  1. ❌ 把数据库异常与刚刚发生的网络维护（43 秒断连）关联起来，而不是当成数据库自身故障
  2. ❌ 识别出现了双主/脑裂：两岸各自接受了对方没有的写入，这才是不能简单切回的原因
  3. ❌ 识别自动故障切换策略本身成了放大器（Orchestrator 跨区提升主库）
  4. ❌ 明确'数据完整性 > 可用性'的取舍，并识别恢复路径自身耗时（备份恢复数小时、副本滞后按幂衰减而非线性）
  5. ➖ 先查最近变更/发布（通用样板，不计分）

### 平台原始输出（逐字）

**根因判定**：命中排查剧本《数据库复制/备份事故（滞后、断链、误删、备份失效）》：数据库事故有三条经典链：①复制滞后→WAL 段在主库被回收→备库断链（没开归档必然发生）；②重建备库时的破坏性操作打在主库上（GitLab 2017 就是这么丢的 300GB）；③备份机制'配了但静默失效'（pg_dump 版本混用、备份桶是空的）。思路：先查复制状态与 WAL 保留 → 再确认主备角色（破坏性操作前必须） → **验证备份真的能恢复**（不信配置，信演练）→ 定位数据丢失窗口。

**置信度**：medium · **大脑**：rule

**排查链**：
- [查复制状态与 WAL 保留] 滞后量、断链时间点、WAL 是否被回收、归档是否真的在工作
- [确认主备角色再动手] 当前连接的是主库还是备库——破坏性操作前必须显式确认
- [验证备份真的能恢复] 备份可恢复 + RPO 覆盖故障窗口 → 才敢动手修
- [定位数据丢失窗口] 丢失窗口 = 故障起始 → 最后备份；窗口越小越好

**验证命令**：
- `pg_stat_replication 滞后量回落到秒级`
- `备库 pg_is_in_recovery()=true 且可持续追赶`
- `恢复演练：从选定备份集恢复到临时实例并抽样校验数据`
- `监控告警：复制滞后阈值告警已恢复`

**🟢 可自动处置**：重建备库（确认目标是备库后，pg_basebackup 到备库）；开启/修复 WAL 归档（主库参数，需重启场景外评估）；清理无用复制槽/连接
**🔴 需审批处置**：主备切换（promote）（brief·DBA + 业务负责人）；从备份恢复数据到主库（full·数据 Owner + DBA）；删除数据目录（任何主机）（full·DBA + SRE on-call）

**修复覆盖对照**：复盘里真正止血的动作是「从备份重建集群 → 同步副本 → 回切原拓扑 → 处理积压（三步走）」（复盘原文：备份每 4 小时一次，恢复数 TB 耗时数小时；恢复完还要等副本追平（滞后按幂衰减））→ 平台**覆盖到了**（白名单对应动作：restore_from_backup）
