## Fastly 2021-06-08 全球 CDN 中断（客户合法配置触发软件 bug）

- 来源（官方复盘）：https://www.fastly.com/blog/summary-of-june-8-outage
- 真实根因（跑前固定）：5 月 12 日部署的软件里有一个未被发现的 bug；6 月 8 日一个客户推送了一次**合法**的配置变更，恰好命中该 bug 的触发条件，导致 85% 网络返回错误。放大因素：新的校验逻辑同步下发到全网（无灰度）；配置校验失败即停止服务，没有回退到上一个好配置的降级路径；验证逻辑与部署逻辑紧耦合，导致校验规则变更立即改变已有生产配置的行为。
- 决定性步骤（跑前固定；➖=通用样板不计分）：
  1. ❌ 先分清 503 是哪一层产生的（CDN 边缘层 vs 源站），而不是被源站被打爆的表象带偏
  2. ✅ 把故障起点与近期的软件版本部署（5/12，数周前）+ 客户侧配置变更做关联
  3. ❌ 识别客户配置是'合法'的：它只是触发器，根因在平台自己的代码里
  4. ❌ 识别 blast radius 是平台全局：同一套校验逻辑同步下发，无灰度、无回退路径
  5. ➖ 先查最近变更/发布（通用样板，不计分）

### 平台原始输出（逐字）

**根因判定**：某客户的配置变更被推送到 edge-cdn 全局配置，导致约 85% 网络在 09:47 起同时返回 503；源站请求暴涨是客户重试与回退逻辑放大的次生现象，而非根因。

**置信度**：medium · **大脑**：openai:deepseek-chat

**排查链**：
- [确认影响面与时间线] 09:47 全球中断开始，09:48 Fastly 监控即发现，约 85% 网络返回 503，多个大型客户站点同时不可访问，属全局性边缘层故障。
- [区分根因与次生现象] 源站侧流量异常暴涨与 503 同时出现，但时间线上中断先发生；源站暴涨可由客户重试与回退逻辑放大解释，故源站容量/攻击为红鲱鱼。
- [定位变更来源] 工程团队在 10:27 定位到是某个客户的配置变更，随后 10:36 受影响服务开始恢复，12:35 缓解，17:25 部署永久修复，处置路径与配置变更根因一致。
- [对照知识库处置规范] 知识库命中 edge-cdn 依赖超时复盘与 Runbook v2，标准流程为确认影响面→回滚/扩容→验证→归档；回滚属 T3 需 SRE on-call 审批，扩容属 T2 可半自动，冻结窗口内禁止自动执行。
- [排查近期变更窗口] 5 月 12 日曾开始一次软件部署，距今近一个月，与本次 09:47 突发中断的时间相关性弱，暂不能作为直接触发因素。

**验证命令**：
- `curl -s -o /dev/null -w '%{http_code}\n' https://<受影响站点域名>/ （多点抽样确认 503 是否仍存在）`
- `curl -s 'http://<prometheus>/api/v1/query?query=sum(rate(edge_http_requests_total{status="503"}[5m]))%2Fsum(rate(edge_http_requests_total[5m]))' （只读查询当前 503 比例）`
- `curl -s 'http://<prometheus>/api/v1/query?query=sum(rate(origin_requests_total[5m]))' （只读查询源站请求速率，判断重试放大是否回落）`
- `curl -s 'http://<config-service>/api/v1/config/changes?since=2026-06-01T00:00:00Z' （只读拉取近期配置变更记录，核对客户配置变更条目）`
- `curl -s https://<status-page>/history.json （只读核对状态页事件时间线与当前状态）`

**🟢 可自动处置**：只读核对当前 503 比例、源站请求速率与配置变更记录，确认影响面是否已收敛；在状态页与客户沟通渠道同步事件进展与已定位的客户配置变更信息
**🔴 需审批处置**：回滚涉事客户的 edge-cdn 配置变更（T3 高风险动作）（brief·SRE on-call）；对 edge-cdn 边缘节点扩容以吸收重试放大流量（T2 中风险，可半自动）（rolling·SRE on-call）

**修复覆盖对照**：复盘里真正止血的动作是「禁用/回退触发 bug 的那个客户配置（先止血），之后再部署永久修复」（复盘原文：定位后禁用了该配置，49 分钟内 95% 网络恢复；永久修复 17:25 才开始部署）→ 平台**覆盖到了**（白名单对应动作：无）

## GitHub 2018-10-21 MySQL 脑裂（43 秒网络分区引发 24 小时降级）

- 来源（官方复盘）：https://github.blog/2018-10-30-oct21-post-incident-analysis
- 真实根因（跑前固定）：例行维护更换光模块造成东西海岸 43 秒网络分区；Orchestrator 把分区判定为主库故障并跨区提升了西海岸副本为主库；链路恢复后两个机房各自接受了对方没有的写入（事实上的脑裂/双主），无法安全切回。放大因素：Orchestrator 的跨区提升策略本身是放大器；跨大陆 60ms 延迟让东海岸应用基本不可用；恢复路径（从远端备份恢复数 TB）从未整体演练过，耗时远超预期。
- 决定性步骤（跑前固定；➖=通用样板不计分）：
  1. ✅ 把数据库异常与刚刚发生的网络维护（43 秒断连）关联起来，而不是当成数据库自身故障
  2. ✅ 识别出现了双主/脑裂：两岸各自接受了对方没有的写入，这才是不能简单切回的原因
  3. ✅ 识别自动故障切换策略本身成了放大器（Orchestrator 跨区提升主库）
  4. ✅ 明确'数据完整性 > 可用性'的取舍，并识别恢复路径自身耗时（备份恢复数小时、副本滞后按幂衰减而非线性）
  5. ➖ 先查最近变更/发布（通用样板，不计分）

### 平台原始输出（逐字）

**根因判定**：计划维护更换100G光模块导致东西海岸骨干断连43秒，东海岸主库与其西海岸副本失联，引发复制中断与不一致读；随后将应用栈整体切至西海岸单主库，跨大陆约60ms往返延迟应用无法承受，导致站点大面积报错、webhook与Pages构建大量积压，且数十个只读副本滞后数小时。

**置信度**：high · **大脑**：openai:deepseek-chat

**排查链**：
- [时间线定位触发点] 22:52计划维护更换故障100G光模块，东西海岸骨干断连43秒，东海岸主库与西海岸副本失联，网络恢复后内部服务开始报不一致读
- [拓扑异常确认] Orchestrator API 复制拓扑中只剩西海岸机房服务器，说明东海岸主库/副本已从拓扑中脱离
- [不一致读与复制滞后] 数十个只读副本落后主库数小时，用户看到前后不一致数据
- [处置动作与副作用] 23:07决定整体切至西海岸让写入汇聚单主库，但跨大陆往返延迟约60ms应用无法承受，导致站点大量报错
- [积压与恢复] 23:19暂停webhook投递与Pages构建，积压500万+ webhook事件、8万Pages构建；次日00:05计划从备份恢复，06:51部分集群恢复完成，23:03积压处理完，总降级约24小时

**验证命令**：
- `SELECT * FROM performance_schema.replication_connection_status\G`
- `SELECT * FROM performance_schema.replication_applier_status_by_worker\G`
- `SHOW REPLICA STATUS\G`
- `orchestrator-client -c topology -i <cluster>（只读查询拓扑）`
- `orchestrator-client -c replication-analysis（只读分析）`
- `ping -c 10 <对端机房主机> 与 mtr -r -c 20 <对端机房主机>（只读测延迟）`
- `SELECT COUNT(*) FROM information_schema.processlist WHERE command='Sleep'（只读观察连接）`

**🟢 可自动处置**：只读确认Orchestrator拓扑与各副本复制状态，记录滞后副本清单；只读测量东西海岸跨大陆RTT，确认60ms延迟是否持续；保持webhook与Pages构建暂停，避免积压继续扩大
**🔴 需审批处置**：将写入主库回切至东海岸或恢复原双海岸拓扑，并重建复制关系（brief·SRE on-call）；对滞后副本执行从备份恢复/重建同步（rolling·SRE on-call + db-infra负责人）；恢复webhook投递与Pages构建并处理500万+积压（none·SRE on-call）

**修复覆盖对照**：复盘里真正止血的动作是「从备份重建集群 → 同步副本 → 回切原拓扑 → 处理积压（三步走）」（复盘原文：备份每 4 小时一次，恢复数 TB 耗时数小时；恢复完还要等副本追平（滞后按幂衰减））→ 平台**覆盖到了**（白名单对应动作：restore_from_backup）
