- **A（规则兜底）10/24 → B（DeepSeek LLM）24/24，+14 分**。提升最大的三类：**配置/权限（S7：0→3）、磁盘容量（S2：1→3）、K8s 镜像层（S4：1→3）**——都是规则大脑"只有一篇知识库文档 + 零推理"完全无法覆盖、需要真实世界推理的场景。
- **关键洞察（面试金句）**：A 轮 7/8 场景被判成"依赖超时"，不是逻辑错误，是**知识覆盖 × 推理能力的双重缺失**；接入 LLM 后不仅判对根因，还会**主动指出知识库不匹配**（S4/S7 明确说"而非知识库中依赖超时场景"）并**建议补充 Runbook**（S7）——这就是 RAG+LLM 相对纯规则系统的本质差异。
- **LLM 的"诚实性"验证**：S3 中 LLM 主动标注"告警文本仅为疑似（suspected），尚未确认"，没有编造确定性结论——与护栏设计的"已知/推测/无法确认"四段式完全同构。
- **工程链路全程正确**（两轮都算）：8/8 场景去重生效、护栏判 T3 → pending_approval、审批后才可执行。
- **成本**：B 轮 8 次研判 ≈ 8 次 DeepSeek 调用，输入约 1K token/次，总成本约 ¥0.05（deepseek-chat 定价）——"LLM 只进 P0/P1 主链路"的分流设计下，单次故障研判成本可忽略。
- **平台边界（如实记录）**：无指标源（Prometheus/Node Exporter 未接）时，S3 的 CPU 故障只能靠日志间接推断，LLM 也明确标注"尚未确认"——接指标源在路线图（夜莺/Keep → /api/ingest）。

# 第二轮：生产级场景盲测（P1-P4，2026-10-25）

> 第一轮（S1-S8）暴露了"日志文本级 demo"的局限：故障是**写进去的字符串**，没有真实资源变化、
> 没有真实服务感知、没有变更台账。第二轮按**生产 SRE 标准**重建：真实服务（payment-api 有真实
> 计算开销的健康检查）+ 真实故障（真进程/真配置变更/真停机）+ 看门狗真实测量 + 变更台账关联。
>
> 被测系统能力：**排查链（investigation chain）+ 验证命令（verification）+ 处置分级（remediation
> grading：🟢可自动 / 🔴需审批+停机风险+审批人）+ 证据关联（证据 + 变更台账）**。

## 场景设计与注入方式（全部自动恢复）

| 场景 | 生产原型 | 注入方式（真实） | 预期排查剧本 |
|---|---|---|---|
| P1 资源抢占 | 隔壁团队批处理作业吃满 CPU（吵闹邻居） | 24 个忙循环 + 120MB 内存扫描进程（make -j24 失控），90s 自愈 | 资源抢占 |
| P2 跨部门变更 | 别的团队改坏我们的 upstream 配置并重启 | sed 改 `/etc/payment-api/config` + systemctl restart，60s 后回滚 | 变更引入故障 |
| P3 内存耗尽 | 内存分析任务持续申请逼近 OOM | 5×280MB 真实触摸页 + 服务内存守卫（可用<1.3GB 报警），80s 自愈 | OOMKilled |
| P4 服务断线 | **租用机器上的服务突然不可用**（用户点名场景） | systemctl stop payment-api，60s 后恢复 | 节点/服务断线 |

关键基建改造（让"变慢"可被真实观测，而不是常量返回的假服务）：
- `payment-api.py` 重写：`/healthz` 真的做上游探测 + 固定工作量计算（约 4ms），**CPU 被抢占时延迟线性上涨**；
- 看门狗每 1s 实测 healthz 耗时，阈值 = max(基线×2.5, 12ms)，超标才写 ERROR 且**自带实测数字**（"latency 57ms vs baseline 8ms, 7x degradation"）；
- 变更台账 `/var/log/changes.log`：每次注入都记录"谁、做了什么、什么时候"——排查时与症状做时间线关联；
- 探针上报前跑只读排查脚本（`investigate.sh`：kubectl/ps/free/systemctl/journalctl/uptime），把**节点侧证据**附在告警里。

| P2 跨部门变更 | upstream 探测失败，服务 degraded，重试 1/5…5/5 | ✅ 变更引入故障 | ✅ 台账：team-billing 09:19:41 改 upstream（未通知、无变更单）——与告警时间差 <10s | 🟢 保留现场摘流量 / 扩容旧版本副本；🔴 rollout undo（rolling，需变更方负责人）/ 删他人 ConfigMap（full） |

## P4 完整证据样本（回答"租用机器服务突然断线怎么排查"）

```
### 6. 系统服务健康
kubelet: active     containerd: active     sshd: active
payment-api: inactive Sun 2026-10-25 09:29     ← 服务自己死了，不是机器死了
-- 机器 uptime: up 14:35, boot: 2026-10-24 08:50   ← 机器没重启 → 排除云平台重装/重启
-- 8080(payment-api): Connection refused 不通       ← 端口层确认
### 5. 变更台账
09:29:43 [team-billing] 在租用机器上执行维护操作（未通知本团队）  ← 告警前 3 秒，强相关
```

排查思路（平台固化为剧本，运维照着走）：**网络层 → 系统层 → 服务层自底向上**——节点在吗？
kubelet 活着吗？运行时活着吗？服务进程活着吗？机器重启过吗（uptime/who -b）？最近谁动过
（台账）？每一步都有只读命令和判据，结论分"已知/推测/无法确认"。

## 这轮验证的能力（相对第一轮的升级）

1. **可观测性基建是前提**：假服务（常量返回）下 CPU 抢占测不出任何现象——先把服务改成有真实开销的，故障才"可见"。这是生产排障的第一课：**没有基线和 SLO，就没有告警**。
2. **证据链闭环**：症状（看门狗实测数字）→ 证据（ps/free/systemctl/台账）→ 剧本（排查链+命令）→ 处置分级（🟢/🔴+审批人）→ dry-run 计划（爆炸半径）→ 人工审批。全程无静默自动执行。
3. **跨团队关联**：台账让"别的团队干了什么"可追溯——P2/P4 的根因线索都来自台账，而不是靠猜。
4. **去重与降噪在真实故障下也成立**：P1 每秒 1 条 ERROR × 90s → 去重后 3 条告警；P4 持续断线 60s → 1 条告警 + 2 次全额去重（累计降噪 56.2%）。
5. **规则大脑的边界如实呈现**：P1-P4 全部命中正确剧本，但"谁在抢资源/配置被谁改了"这类**关联推理**规则大脑做不到（输出明说"请以剧本排查链人工确认，接 LLM 后可自动推理"）——这正是 LLM 大脑的增量价值（同 S 轮结论）。

# 第四轮：补剧本 + 自动修复 + 自愈实测 + 留出集（2026-10-25）

> 上一轮暴露"剧本库缺三类（运维变更/数据库/网络）"，本轮补齐并往"能不能真修好"推进。
> 用户要求"放开权限让 AI 直接修"——**我没有做无护栏全自动**，理由是：在一个留出集
> 只有 2/6 的系统上放开写权限，是把小故障放大成事故的标准姿势。取而代之做的是
> **动作白名单 + 有界爆炸半径 + 执行后验证 + 失败回滚 + 全程审计**，这也是 AWS/Google
> 生产 auto-remediation 的真实形状。
