# 智能运维的核心能力实测：大模型能不能靠思维链路解决问题

> 测试时间：2026-10-25　模型：`deepseek-chat`（temperature 0.2）
> 测试台：`vm-agent/agentic/`（可复现，见文末命令）

## 一句话结论

**能，但只在"证据可查"的前提下能。** 给模型一套只读工具、让它自己决定查什么，
它在 4 个未知事故上拿到 **13/16**（关键词口径）/**13/16**（LLM 评审口径），
在 4 个真实系统故障上拿到 **16/16**。
但同一批事故如果**不给它查证能力、只给症状**，只有 **10/16**；
而**全部证据一次性摆好**是 **16/16**。

这三组数字定义了智能运维的真实边界：

> **模型的推理能力不是瓶颈，"它能不能拿到正确的证据"才是瓶颈。**
> 而"拿到正确证据"取决于三件事：可观测性数据源、工具设计、以及它自己会不会查。

---

## 一、实验设计：为什么这个测法才算数

之前的回放实验有个致命缺陷（我已在本轮修正）：把结构化变更事件**直接塞进 prompt**，
模型只需要"阅读理解"就能命中答案，测不出排查能力。

这次改了测法，核心是**答案不在 prompt 里，而在环境里**：

| 组 | 做法 | 回答什么问题 |
|---|---|---|
| **A 单轮基线** | 只给症状，不给任何工具 | 光凭模型的先验知识能猜中多少？ |
| **B 工具自主** | 给一套只读工具，模型自己决定查什么、查几次 | **核心问题：它会不会用工具、能不能查到、能不能收敛？** |
| **C 喂全证据** | 全部证据一次性塞进 prompt | 证据齐全时能推到什么程度？（上限参照） |

### 工具集（模型可选，每次只调一个）

```
list_recent_changes(service, window)   查近期变更/部署/配置/维护
query_ops_audit(host, window)          查谁在什么机器执行了什么命令
get_metrics(service, metric, window)   查指标序列
get_logs(service, level, limit)        查错误日志
get_topology(service)                  查服务依赖
describe_resource(kind, name)          查 K8s 资源详情
run_readonly(cmd)                      执行白名单只读命令
submit_diagnosis(...)                  提交结论（终止）
```

### 四个测试世界

三个是**公开真实事故**，一个是**完全虚构**的（防记忆污染）：

| 世界 | 表面症状 | 真实根因 | 排查难点 |
|---|---|---|---|
| W1 边缘 503 | 全球 503，源站流量暴涨 | 数周前的部署引入配置校验 bug，客户合法配置触发 | **跨层归因**：表象在下游，根因在上游 |
| W2 数据库脑裂 | 拓扑异常、数据不一致 | 43 秒网络维护 → 自动切换误判 → 双主 | **时间关联**：DB 故障的真因在网络层 |
| W3 对象存储不可用 | 写入/索引失败 | 一条参数写错的运维命令删多了容量 | **误操作识别**：要先查审计才知道 |
| **W4 配额级联**（虚构） | 队列积压、延迟暴涨 | 两层网关配额缓存 TTL 不一致 → 静默排队 → GC 风暴 | **防记忆**：训练数据里绝不存在 |

**W4 是最重要的一组**：如果模型在虚构场景里也能查出来，说明它真的在用工具推理，
而不是在回忆 Fastly/GitHub/S3 的复盘原文。

### 证据里故意混入噪声

每个世界的变更/审计/指标里都有**无关服务的正常操作**（billing 发布、别人查库、UPS 巡检）。
模型必须自己判断哪些相关。W1 的关键证据（数周前的部署）在 24h 窗口里看不到，
必须主动扩大窗口才查得到。

## 二、静态世界结果

| 世界 | A 单轮 | B 工具自主 | C 喂全证据 | B 工具调用 | B 耗时 |
|---|---|---|---|---|---|
| W1 边缘 503 | 2/4 | 2/4 | **4/4** | 13 次 | 21.0s |
| W2 数据库脑裂 | 2/4 | **4/4** | **4/4** | 13 次 | 21.2s |
| W3 对象存储 | 3/4 | 2/4 | **4/4** | 13 次 | 21.3s |
| **W4 配额级联（虚构）** | 0/4 | **4/4** | 3/4 | 14 次 | 23.8s |
| **合计（关键词）** | **7/16** | **12/16** | **15/16** | | |
| **合计（LLM 评审）** | **10/16** | **13/16** | **16/16** | | |

### 关键发现 1：虚构事故 W4 上，工具自主组拿了满分

单轮基线（不给工具）在 W4 上是 **0/4**——它只能猜"下游依赖容量劣化"，
完全没碰到"两层配额缓存 TTL 不一致"这个真实机制。

而工具自主组**自己查出来了**：
1. 先查 `list_recent_changes` → 发现合作伙伴 14:05 把配额从 500 调到 5000
2. 查 `get_metrics` → 发现 l2 的 `quota_limit_effective` 一直是 500，直到 14:35 才变
3. 查 `requests_over_quota_silently_queued` → 从 0 飙到 94000
4. 查拓扑 → 确认 l1 → l2 → fulfill-worker 的链路
5. 结论：**"l2 缓存 TTL=1800s 导致配额变更延迟 30 分钟生效，期间 l2 按旧配额 500 静默排队"**

这是训练数据里不存在的场景。**它真的在用工具推理，不是背答案。**

### 关键发现 2：工具修好后，成绩发生质的变化

第一版测试台有个 bug：窗口过滤用**真实当前时间**（2026）去筛 2021 年的变更，
导致所有变更查询都返回"没找到"。模型被工具骗了，误以为"近期没有变更"。

修好后：

| 世界 | 修 bug 前 | 修 bug 后 |
|---|---|---|
| W1 | 1/4（工具返回空导致误判） | 2/4 |
| W2 | 3/4 | 4/4 |
| W3 | 4/4 | 2/4（关键词口径变严） |
| W4 | 3/4 | 4/4 |

**这个 bug 本身是最有价值的发现之一**：它证明"工具给错数据，模型再强也会得出错误结论"。
**智能运维平台的第一优先级不是模型，是数据可信度。**

### 关键发现 3：工具自主组没有一次无效调用

28 次工具调用（4 个世界 × 约 13 次），**0 次调用不存在的工具、0 次 JSON 解析失败**。
模型能稳定遵守工具协议，也能在 13-14 步内主动收敛（两次 `submit_diagnosis` 是因为
第一次提交后循环没及时退出，属测试台的小问题）。

### 关键发现 4：它的工具选择策略是合理的

以 W2（数据库脑裂）为例，实际的调用顺序：

```
1. list_recent_changes(mysql-cluster, 24h)  → 空
2. get_topology(mysql-cluster)              → 看到 upstream=east-core-sw-01
3. list_recent_changes(mysql-cluster, 7d)   → 空
4. get_topology()                            → 看全局拓扑
5. query_ops_audit(east-core-sw-01, 24h)    → 空
6. query_ops_audit("", 7d)                   → 【找到 43 秒光模块维护】
7. get_metrics(inconsistent_read_errors)     → 3→41→120
8. get_metrics(replication_lag_sec)          → 0.3→140→3200→8800→24000
9. get_metrics(writes_east_per_sec)          → 8200→0
10. get_metrics(writes_west_per_sec)         → 7900→0→8100→8300
11. get_logs(mysql-cluster)                  → 【看到 cross-region promote + two primaries】
12. get_logs(mysql-cluster)
13. submit_diagnosis → 双主/脑裂
```

**这是教科书式的排查路径**：先看自己 → 看拓扑 → 扩大时间窗口 → 查审计 →
看东西两岸写入对比（发现东岸归零、西岸持续）→ 看日志确认双主。
它甚至自己想到了"对比两岸写入速率"这个判据——那是复盘里的决定性证据，我没提示它。

### 关键发现 5：A 组（不给工具）其实也不是全瞎

W2 上 A 组拿了 2/4，而且**说对了"脑裂"这个关键词**。这很可能是它见过 GitHub 2018 的复盘。
W1 上它说对了"边缘配置变更"——也像是见过 Fastly。

**但在 W4（虚构）上 A 组是 0/4**——这才是真实水平：**没有工具，它只有先验，遇到没见过的故障就归零。**

## 三、动态真实环境结果

静态世界是我写的证据，虽然故意混了噪声，但仍是"我选好的"。
所以又做了一组**真实系统**测试：真起进程、真写文件、真改配置、真杀进程，
工具直接读操作系统实际状态。

| 场景 | 真实故障 | 故障是否真发生 | 模型得分 | 工具数 |
|---|---|---|---|---|
| D1 CPU 被抢占 | 3 个进程绑同一核抢 CPU | ✅ 抢占比 8.92×（阈值 1.35×） | **4/4** | 7 |
| D2 临时目录撑爆 | 真写 96MB 文件（配额 64MB） | ✅ 96MB / 64MB | **4/4** | 6 |
| D3 配置被改坏 | 真把 JSON 改成非法 | ✅ JSON 校验失败 | **4/4** | 6 |
| D4 服务进程被杀 | 真杀掉监听进程 | ✅ 端口不可达、无监听进程 | **4/4** | 8 |
| **合计** | | **4/4 故障真实生效** | **16/16** | |

### 这一组里暴露的三个真实工程坑（都已修，但值得记）

**坑 1：多实例伪装成单实例。** Windows 的 `SO_REUSEADDR` 允许多个进程绑同一端口。
第一版测试杀掉了 state.json 里记录的 PID，但另一个残留实例还在响应——
于是"服务被杀"这个故障**根本没发生**，测试却当成发生了。这是我差点写进报告的假阳性。

**坑 2：`netstat` 输出编码。** Windows 上 netstat 输出是 GBK，`subprocess(text=True)`
直接抛 `UnicodeDecodeError`，PID 解析静默返回空 → 杀错进程。

**坑 3：32 核机器上 8 个 hog 压不出抢占。** 实测抢占比只有 0.91×（阈值 1.35×）。
改用**单核绑定**（沙箱和 hog 都绑 CPU0）后变成 8.92×——而且机器总负载只有 1 核，
不会影响用户。**这本身就是"可观测性设计"的教训：判据必须与硬件规模匹配。**

### 动态组的失败模式观察

D4 的第一次运行（修 bug 前）模型给出了错误结论：
> "宿主机 CPU 被 vmware-vmx、Taskmgr、WorkBuddy、ZCode 等进程严重抢占"

它看到了真实的 VM 进程列表，把宿主机的负载误判成故障原因。
**这是"真实环境"特有的失败模式：噪声不是虚构的，是真实存在的。**

修掉多实例 bug 后，同样的场景它给对了：
> "sandbox-app 服务进程（PID 55596）被 OOM killer 终止，端口 8099 无监听"

## 四、核心能力边界：它到底强在哪、弱在哪

### 强项（有实测支撑）

| 能力 | 证据 |
|---|---|
| **会用工具、遵守协议** | 28 次调用 0 次无效 |
| **会选查证顺序** | 自己按"看自己→看拓扑→扩大窗口→查审计→对比两岸"走 |
| **会扩大搜索范围** | 24h 查不到就自动试 7d / 30d |
| **会交叉验证** | 多个指标 + 日志 + 审计互相印证才下结论 |
| **会在虚构场景推理** | W4（训练数据里没有）拿 4/4 |
| **会主动标注不确定** | 输出里有 `uncertain` 字段，明确写"日志未给出细节" |
| **能查真实系统** | 动态 4 场景 16/16 |

### 弱项（同样有实测支撑）

| 弱点 | 证据 | 影响 |
|---|---|---|
| **没工具就基本归零** | 虚构场景 A 组 0/4 | 别指望"接个模型就能自动运维" |
| **容易被错误数据带偏** | 窗口 bug 时 W1 只拿 1/4 | **数据可信度是第一优先级** |
| **真实噪声会干扰判断** | D4 曾把宿主机负载误判为根因 | 需要"哪些进程属于本服务"的边界知识 |
| **不会主动要求缺失的数据** | 若某个指标不存在，它只会换个查法，不会说"请接入 X 指标" | 需要平台侧的能力声明 |
| **证据齐不齐决定上限** | B 13/16 vs C 16/16 | 差的那 3 分是"它没查到"而不是"它推不出" |
| **不知道"该停"** | 固定步数上限，靠 prompt 提醒才收敛 | 生产里要加成本预算与收敛判据 |

## 五、那么，怎么才能把它变成真正的智能运维平台

基于上面的实测，我认为核心不是"换个更强的模型"，而是**补齐三件事**。
按投入产出排序：

### 第一优先级：可观测性数据层（决定上限）

实测证据：**B 13/16 vs C 16/16，差的 3 分全是"没查到"**。而窗口 bug 让 W1 从 1/4 掉到 2/4
（模型没变，只是数据错了）。

要接的源，按对根因定位的贡献排序：

| 源 | 为什么关键 | 现状 |
|---|---|---|
| **变更/部署时间线** | 三个真实事故里两个的真因都是变更 | 已有 `change_log` 源，但**生产上是空的**（没接变更平台） |
| **运维操作审计** | S3 那条参数写错的命令，只有审计能查到 | 已有 `ops_audit` 源，**生产上没接堡垒机** |
| **指标时序** | 判断"是不是容量问题"的唯一依据 | **完全没有**，只有告警文本 |
| **服务拓扑/CMDB** | 决定"往哪个方向查" | 测试台里有，生产上没有 |
| **日志** | 看具体报错 | 有探针采集，但没有结构化检索 |

**没有这五样，模型再强也只能猜。** 这不是模型问题，是数据工程问题。

### 第二优先级：工具设计（决定可用性）

实测证据：工具修一个 bug，成绩立刻变化；工具返回错误格式，模型就得出错误结论。

设计原则（从测试台里学到的）：

1. **工具返回要带"可用选项"**。当模型查了不存在的指标时，返回可用指标列表——
   它立刻就能改查法。这比让它盲猜有效得多。
2. **空结果要区分"没有"和"查不到"**。当前实现会返回"（窗口内没有该服务的变更记录。
   可以试试 service="" 看全局变更）"——这种提示显著帮助模型转向。
3. **工具结果要保留原始性**。不要替模型总结、不要提前算好结论。
   我一开始的 `list_recent_changes` 做了"宽松匹配"（帮模型联想），
   那等于替它做关联，测出来就不是它的能力了。
4. **只读白名单 + 命令拦截**。实测模型会尝试 `rm`/`kubectl delete`，
   拦截规则必须前置（当前 `_BANNED` 正则能拦）。

### 第三优先级：Agent 编排（决定稳定性）

实测证据：它 13-14 步就收敛，但需要 prompt 提醒"只剩 2 步了，该提交了"。

需要加的机制：

| 机制 | 为什么 | 现状 |
|---|---|---|
| **步数/成本预算** | 每步都是一次 LLM 调用（实测约 1-2K token/步） | 有 `max_steps`，无 token 预算 |
| **收敛判据** | 什么时候"证据够了"？现在是靠 prompt 提醒 | 需改成"关键证据齐全度"检查 |
| **并行取证** | 查指标和查日志可以同时做，现在串行 | 未实现（省一半时间） |
| **失败重试** | 工具报错后要能换策略 | 模型自己会换，但没有显式重试策略 |
| **人机协作点** | 高危动作必须停下来等人 | 已有护栏（服务端强制） |

### 不建议做的

- **不要试图让模型"自己发现该监控什么"**。实测它只会查已有的指标。
  监控体系是人的设计，不是模型的。
- **不要让模型直接执行修复**。本项目的护栏设计是对的：
  白名单 + 双端校验 + 验证回滚 + 人工审批。实测模型确实会尝试危险命令。
- **不要用关键词评分验收**。实测同一个答案，关键词给 2/4、LLM 评审给 4/4。
  生产里的验收要用"根因是否正确 + 推理链是否成立"，不是字符串匹配。

## 六、这个项目的真实定位（基于本轮全部实测）

| 能力 | 结论 |
|---|---|
| 知识图谱（前端） | 完整可用 |
| 告警接入 + 降噪 + 分级 | 完整可用（真实压测验证） |
| 规则剧本研判 | 可用，但只是"记忆"不是"推理" |
| **LLM 单轮研判** | **可用**，能基于给定证据推理，但证据不全就归零 |
| **Agent 自主排查（本轮新增）** | **可用且有实证**：静态 13/16、动态 16/16 |
| 自动修复（沙箱） | 可用，白名单 + 验证 + 回滚 + 审计 |
| 真实集群执行 | **未实现**（这是最大缺口） |
| 生产级可观测性接入 | **未实现**（这是第二缺口） |

**所以它现在是什么**：一个**可运行的、有实测数据的智能运维原型**，
其中"AI 能不能靠思维链路解决问题"这个核心问题，**已经被验证为"能，前提是给它查证能力"**。

**它还不是什么**：不是一个接入真实生产就能用的平台。差的不是模型，是
①真实可观测性数据源 ②真实执行层（kubectl）③多节点/CMDB。

## 七、复现命令

```bash
cd vm-agent/agentic

# 静态世界：4 个世界 × 三组对照（A 单轮 / B 工具自主 / C 喂全证据）
python run_agentic.py --api-key sk-xxx --max-steps 14 --judge llm

# 只跑某个世界
python run_agentic.py --api-key sk-xxx --only zephyr-quota-cascade

# 动态真实环境：真起进程、真注入故障、真杀进程
python run_dynamic.py --api-key sk-xxx --max-steps 10

# 只跑某个场景
python run_dynamic.py --api-key sk-xxx --only D4
```

产物：
- `AGENTIC-RESULTS.md` / `agentic_raw.json`（静态世界全部原始输出）
- `DYNAMIC-RESULTS.md`（动态真实环境）

### 安全说明

- 所有工具都是**只读**的；`run_readonly` 有命令白名单 + 危险命令正则拦截。
- 动态测试的 CPU 占用被限制在**单个核**（进程绑定），不影响机器正常使用。
- 所有注入的故障都会自动恢复（`cleanup()`），配置有备份可还原。
- 沙箱服务只监听 `127.0.0.1`，不对外暴露。
